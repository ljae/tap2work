## 1. 증거 수준과 현재 범위

| 표시 | 의미 |

### 운영 관찰과 이미 수행한 조치

- 요청된 계정의 단독 소속 매장 5개를 비공개 백업 후 초기화했다. 인증 계정은 유지했다. 계정 식별자, 이메일, 백업 내용·경로, 상세 주소를 이 문서에 기록하지 않는다.
- 웰컴 확인에서 HTTP 409가 발생하는 현상을 재현했다. 다른 동료가 실제로 수정했다는 증거는 없었다.
- 원인은 JSONB 왕복 과정의 객체 키 순서를 `JSON.stringify` 문자열로 비교하여 공용 매뉴얼의 같은 `knowledge` 내용을 변경으로 인식한 것이다. 반복 조회가 revision을 갱신하여 단독 사용자 저장도 충돌했다. 일반적인 동시 편집 가능성과 이번 사건의 확인된 원인을 구별한다.
- 내용의 구조적 동등성을 비교하도록 최소 수정했다. 회귀 테스트 2개는 수정 전 실패하고 수정 후 통과했다. 서버 테스트 335개, JavaScript 검사·UI 연결 69개, 인증 Deno Edge 검증이 통과했다.
- Sol low 배포 담당이 커밋 `c165363`, operations API **v59 ACTIVE**를 확인했다. 웹·네이티브 바이너리는 이 서버 수정 때문에 재빌드하지 않았다. 유료 번역 비활성·비공개 사진 설정을 유지했다.
- 수정 후 실제 인증 매장에서 **웰컴 확인 저장에 성공**했다. 실제 GET 3회가 모두 HTTP 200, revision 3으로 유지되어 내용 변경 없는 조회의 반복 revision 증가가 멈춘 것을 확인했다. 이 결과를 모든 폼·영업일 전환의 충돌 복구 검증으로 확대하지 않는다.
- 첫 매장 등록을 완료하고 매뉴얼 29개·메뉴 2개·오늘 업무 16개를 확인했다. 가상 크루를 베트남 국적·베트남어 안내·시급제로 등록하고 영업일 6일의 Dishwashing 오픈 교대에 배정했다. 이는 명부/배정 검증이며 별도 크루 인증 로그인 검증이 아니다.
- 주말 종료만 익일 02:00으로 변경했으나 **주말 교대 경계가 16:00에서 15:00으로 함께 변경되는 문제를 실제로 발견**했다. 요일 휴무와 주중 시간은 유지되었다. A15에 원인과 회귀 기준을 분리했다.
- 실제 화면의 “매장 준비 4/4”를 확인했지만 하루 파트×교대 슬롯 12개 중 11개는 크루가 미배정이었고 가격·재고·공급처도 미설정이었다. A10은 소스 위험에서 운영 관찰 항목으로 갱신했다.
- 베트남어에서 주요 메뉴와 행동 설명은 번역되지만 선택한 TAP 상단 제목·완료 카운터와 장소 안내 링크는 한국어로 남았다. 원문 보기로 한국어 전환은 정상 작동했다. A16에 번역 호출 누락을 기록했다.
- 행동 슬라이드 1→2를 탐색해도 완료 기록은 생기지 않았다. 2번 행동의 체크만 저장되고 3번으로 자동 이동했다. 원문 보기 또한 다른 행동을 완료하지 않았다. 감사 후 개인 언어 설정은 한국어로 되돌렸다.
- 공통 폐기물 장소를 잔반통에 연결하고 가상의 매장 규칙으로 웰컴 중요 변경을 저장했다. 열린 웰컴을 중요 변경한 뒤 첫 “업무로 가기”에 웰컴이 즉시 다시 열리고 두 번째에 진입하는 A17을 발견했다.
- 이후 메뉴 가격 11,000원 설정과 가상 메뉴 두부구이 8,000원 추가를 완료했다. 가상 재료 깻잎을 봉 단위·가상 공급처 A·냉장고 위치·최소 5/발주 10/단가 2,000원/발주 후 3일 점검으로 설정했다. 실측 3 → 앱 내 데모 발주 10 후에도 재고 3 → 전량 입고 후 13을 확인했고 점검 예정일은 입고 후에도 10/13으로 유지됐다. 외부 공급자 주문·결제·메시지 발송은 없었다.
- 처음 생성된 재료 7개는 미실측·기준 미확인 상태의 재고 0/최소 0인데 모두 부족/보충 대상으로 표시됐다(A18). 미지정 위치에는 “null · 공급처 미설정”이 표시됐다(A19). 초기 미설정 시점의 A10 관찰과 이후 일부 기준을 입력한 최종 상태를 구별한다.
- 1층 기존 장소 4개와 새 4인 테이블의 배치 초안을 만들었다. 겹침 거절과 화면의 1부터 시작하는 좌표 범위 검증은 확인했다. 위치를 조정해 겹침을 해소한 후에도 “다른 층의 장소는 이 배치에서 수정할 수 없어요.” HTTP 400으로 저장이 막혔다(A20). 요청과 초안을 비공개로 보관한 뒤 UI에서 취소했으며 **배치도 변경은 하나도 저장되지 않았다.** 장소 목록 6개 저장과 배치도 저장 성공을 구별한다.
- 반납대 장소에 **TEST DIAGRAM이라고 표시한 합성 도식**을 앨범 선택 → 미리보기 → 장소 저장 → 다시 열어 표시하는 실제 왕복을 완료했다. 실제 업장 사진이 아니다. Storage 확인 결과 원본 1600×1000 PNG는 1280×800 JPEG, 29,917바이트로 변환됐고 비공개 참조 1개로 저장됐다. 실카메라 촬영·HEIC는 검증하지 않았다.
- 최종 읽기 전용 확인(revision 26): 매장 1개, 실제 인증 멤버 1명, 크루 명부 2명(사장님+가상 크루), 장소 6개 모두 미배치(`mapped:false`), 재료 8개, 메뉴 3개, 매뉴얼 30개, 오늘 업무 18개, 전량 입고된 앱 내 데모 주문 1개(10봉), 해당 재고 13봉. 처음 생성된 매뉴얼 29개·업무 16개와 후속 설정 후 수치를 구별한다.
- 정산은 월 단위·매월 1일·반올림 없음·5인 이상으로 저장했고 `configured:true`, 주휴 설정 기본값 `true`를 확인했다. 실제 지급은 하지 않았으며 설정 저장을 급여 산정의 적법성·정확성 검증으로 간주하지 않는다.
- 주문 보드 ON 저장에 성공했다. 화면은 외부 연결이 없고 예시 주문용임을 명시했다. POS·배달 서비스 외부 연결은 수행하지 않았다.
- 직책 권한의 크루 탭에서 5개 토글이 모두 켜져 있었지만 “기존 직책 권한 범위 안에서만”이라는 제한 안내가 있었다. 실제 허용 권한을 테스트하지 않았으므로 권한 우회 오류로 단정하지 않는다. 설정값과 최종 유효 권한을 사용자가 혼동하는지 A13 검증에 추가했다. 권한 설정은 변경하지 않았다.
- 출퇴근 인증 화면의 위치/Wi-Fi는 미리 선택하는 설정이며, 현재는 직접 버튼을 사용하고 자동 감지는 기기 연동 후 사용한다는 안내를 확인했다. 실제 출퇴근·위치/Wi-Fi 감지는 수행하지 않았다.

## 2. 우선순위와 실행 순서

P0는 기본 사용을 막거나 저장 신뢰성을 훼손하는 항목, P1은 실제 운영과 신입 안내에 필요한 항목, P2는 사용 부담을 줄이는 항목이다. 권장 순서는 **A01 완료 확인 → A02/A03 저장 복구 → A15 시간 설정의 예기치 않은 변경 방지 → A04 실제 크루 연결 → A05~A10 업무 안내 → A11~A14 나머지 운영 검증**이다. 소규모 코드 수정과 제품 정책 결정은 분리한다.

| ID | 우선순위 | 항목 | 증거 | 상태/선행 조건 |
|---|---|---|---|---|
| A01 | P0 | 단독 사용자 revision 반복 증가 | 운영 재현·원인 확인 | 수정 배포·웰컴 성공·GET 3회 revision 유지 확인 |
| A02 | P0 | 충돌 원인 문구와 초안 복구 | 소스 확인 | A01과 별도 후속 |
| A03 | P0 | 크루 저장 실패 시 폼 초안 유실 | 소스 확인 | 저장 흐름 수정 필요 |
| A04 | P0 | 실제 인증 크루 초대·기존 크루 연결 | 소스 확인·현재 불가 | 권한·연결 정책 결정 필요 |
| A05 | P1 | 신입이 일반 루틴의 수행 불가를 보고 | 소스 확인 | 상태·해결 권한 결정 필요 |

## 3. 항목별 구체 작업과 완료 조건

### A01. 단독 사용자 충돌 원인 수정의 운영 확인

사장님은 혼자 처음 설정하고 있는데 동료가 수정했다는 메시지를 받았다. 이미 배포한 최소 수정의 범위를 넘어 전체 충돌 문제가 해결됐다고 결론 내리지 않는다.

- [x] 객체 키 순서만 다른 공용 매뉴얼 knowledge를 같은 내용으로 비교.
- [x] 연속 조회의 revision 유지, 단독 웰컴 확인, 실제 내용 변경 반영, 오래된 요청의 409 거절을 회귀 테스트.
- [x] operations v59 배포 확인.
- [x] 새 매장 등록 후 웰컴 확인 저장 성공, 실제 GET 3회 모두 HTTP 200·revision 3 유지.
- [ ] 별도 완전 재로그인/다른 기기에서도 웰컴 확인 기록 유지.
- [ ] 아무것도 수정하지 않고 30초 폴링을 여러 차례 거친 뒤 설정 저장 성공.
- [ ] 실제 같은 항목을 다른 화면에서 변경하면 기존 revision 검사가 여전히 거절하고 초안을 보존.

### A02. 충돌 문구와 재시도

근거: `developer/operations.mjs`의 revision 불일치 응답은 변경 주체를 확인하지 않고 동료 변경으로 설명한다. `OperationsController.act`는 409 뒤 최신 snapshot을 읽지만 폼의 opening revision을 무조건 갱신하지 않는다. `store_profile_screen.dart`는 다시 열기를 안내한다. 자동 생성·본인 다른 탭·실제 타인 편집을 한 문구로 단정하면 사용자가 불필요하게 계정 공유를 의심한다.

- [ ] 원인을 단정하지 않는 “최신 내용과 차이가 있어 저장하지 못했어요. 입력한 내용은 유지했어요.” 계열 문구와 다음 동작 제공.
- [ ] 원래 값·최신 값·내 초안을 비교해 동일 필드 변경과 무관 영역 변경을 구분.
- [ ] 무관 영역만 바뀐 경우 안전한 재시도, 같은 필드 충돌은 비교 후 선택. revision 숫자만 올려 덮어쓰지 않음.
- [ ] 테스트: 단독 폴링, 영업일 전환, 본인 다른 탭, 같은 필드 충돌, 네트워크 단절, 재시도 중 매장 전환.

완료 조건: 입력 재작성 없이 복구할 수 있고 실제 동시 수정은 조용히 덮어쓰지 않는다.

### A03. 크루 등록/수정 초안 유지

근거: `app/lib/ui/team_screen.dart:246–272`는 저장 버튼에서 폼을 먼저 닫고 controller를 dispose한 다음 `save_tapper`를 호출한다. HTTP 409/네트워크 실패 시 입력 폼이 남아 있지 않는다. 이번 운영 브라우저에서 실패를 재현한 것은 아니다.

근거: `team_screen.dart`의 “코드·QR로 초대”는 `workplace_screens.dart:1365`로 이어지지만 현재는 체험용 코드다. 실제 계정 가입·권한 부여·메시지 발송은 연결되지 않았다고 화면에서 명시한다. 크루 명부 등록을 인증 계정 연결 성공으로 간주할 수 없다.

### A09. 설거지 본보기의 현장 완성도

근거: `docs/market/current.json:378–413`의 “설거지 구역 정리 확인”은 일반적인 3단계이며 사진은 비어 있다. 화면의 사진 기능 구현과 실제 매장에 맞는 상세 본보기 완성은 다르다. 공통 장소 설정이 폐기물·비품 2종인 점은 실제 화면에서도 확인했다. 반납대·잔반통·세척대·건조대 등 6개 장소와 안내 및 반납대 합성 도식은 저장했다. 실업장 사진과 모든 행동의 연결은 미완료다.

- [ ] 사장님이 현장 내용을 바꾸면 원본과 수정 상태를 구별하고 변경 필드의 번역 필요 표시.

- [ ] 열려 있는 동안 본인 중요 편집, 다른 주체의 중요 변경, 일반 변경, 계정/매장 전환, 수동 다시보기 각각 검증.
- [ ] 회귀: 중요 변경 내용이 나타난 열린 웰컴에서 한 번 “업무로 가기” → 업무 진입, 같은 버전 즉시 재등장 없음, 미확인 상태는 유지.

완료 조건: 중요 변경은 최신 내용으로 안내하면서 업무 진입을 한 번의 명시 동작으로 허용한다. 재확인 요청과 실제 확인 이력이 정확히 구별된다.

### A18. 아직 세지 않은 초기 재고가 모두 부족으로 분류됨

**실제 운영 재현, 수정 미실시.** 메뉴에서 생성된 초기 재료 7개는 실제 수량을 세지 않았고 최소/발주 기준도 검토하지 않았지만 재고 0·최소 0을 기준으로 모두 보충 대상으로 표시됐다. 사장님은 “설정 전”을 “실제 품절”로 오해할 수 있으며 일괄 발주 후보에도 잘못 포함된다.

소스 근거: `operations_screen.dart:396–402`와 1293행은 `qty <= min`으로 부족을 계산하며 `setupNeedsReview`/`lastCheckedAt`를 고려하지 않는다. 1223행의 일괄 추가는 발주량의 기본값 1을 사용할 수 있다. 새 재료의 초기 0과 실제 실측 0을 구별해야 한다.

- [ ] 수량 미확인과 최소/발주 기준 미확인을 별도 상태로 표시하고 실측·기준 설정으로 바로 이동.
- [ ] 실측하지 않았거나 발주 기준 미검토인 항목은 자동 부족 요약/자동 일괄 발주 대상에서 제외하고, 명시적 검토 후 추가.
- [ ] 실제 실측 0·확인된 최소 5는 정상적인 부족 항목으로 유지. 0을 일괄 무시하지 않음.
- [ ] 수량은 확인했지만 공급처/발주 단위가 없는 경우 필요한 정보만 안내하고 임의 기본 수량으로 주문 준비를 완료하지 않음.
- [ ] 회귀: 초기 미실측 0/최소 0, 실측 0/최소 5, 실측 3/최소 5, 충분한 수량, 미등록 공급처, 검토 완료 후 일괄 발주 포함.

완료 조건: 첫 설정 직후 사장님이 품절 경고를 정리하느라 불필요하게 발주하지 않고, 실제로 부족한 재료만 정확한 단위·수량으로 발주 후보에 포함된다.

### A19. 재고의 미지정 장소에 내부값 null 표시

**실제 운영 재현, 수정 미실시.** 미지정 재고 카드가 “null · 공급처 미설정”으로 표시됐다. 장소 등록 누락인지 앱 오류인지 사용자가 판단하기 어렵다.

소스 근거: `developer/store_bundle.mjs:37`의 초기 재료는 `zone: null`이다. `operations_screen.dart:1272`에서 이를 `zoneName(i['zone'])`으로 전달하고, 381행의 lookup fallback이 받은 값을 반환하여 표시 문자열에 내부 null이 노출된다.

- [ ] nullable 장소 입력을 명시적으로 처리하여 “보관 장소 미설정” 같은 번역된 안내 표시.
- [ ] 장소가 삭제/보관되어 참조를 찾지 못하는 경우와 아직 연결하지 않은 경우를 구분하고 설정 진입 제공.
- [ ] null·빈 문자열·없는 장소 ID·정상 장소를 회귀 검사. 사용자가 등록한 정상 이름을 임의 대체하지 않음.

완료 조건: 재고 카드에 null/내부 ID가 노출되지 않고 사장님이 무엇을 설정해야 하는지 바로 알 수 있다.

### A20. 새 테이블의 좌표를 다시 편집하면 층 정보가 사라져 저장 불가

**실제 운영 HTTP 400 재현, 수정 미실시.** 1층 배치 초안에 기존 장소 4개와 새 4인 테이블을 추가했다. 최초 겹침/범위 검증을 통과하도록 좌표를 조정한 후 저장했지만 “다른 층의 장소는 이 배치에서 수정할 수 없어요.”로 거절됐다. 사용자는 같은 1층만 편집했으므로 안내 문구만으로 해결하기 어렵다. 실제 실패 POST와 초안은 비공개 보관 후 화면에서 취소했으며 운영 배치에는 변경이 반영되지 않았다.

원인: `app/lib/ui/floor_plan.dart:941`은 새 항목을 처음 추가할 때만 `floor`를 붙인다. 같은 초안의 좌표를 재편집하면 `_ItemDialog`(1418행)는 `floor` 없이 새로운 map을 반환하고 944행은 기존 항목을 이 map으로 교체한다. 아직 서버에 없는 신규 테이블은 이전 층 정보도 없으므로 `developer/layout.mjs:48`의 검증에서 빈 층과 `floorScope`인 1층이 다르다고 판단한다. 캡처한 요청의 새 테이블에 해당 층만 보완한 로컬 검증에서는 통과했고 2층 장소 2개도 보존됐다. 이는 로컬 원인 검증이며 운영 저장 성공이 아니다.

- [ ] 항목 재편집은 기존 메타데이터를 보존하면서 편집한 필드만 덮어쓰고, 새 항목에는 현재 층을 유지.
- [ ] floor 외에 장소 사진·구역·미배치 상태 등 편집 폼이 소유하지 않는 메타데이터의 보존 계약도 점검.
- [ ] 서버의 다른 층 수정 차단을 제거하거나 모든 항목의 층을 일괄 변경하는 방식으로 우회하지 않음.
- [ ] 회귀: 1층 새 테이블 추가 → 좌표/크기/좌석 재편집 → 저장 성공, 새 테이블의 1층 유지.
- [ ] 회귀: 기존 1층 장소의 사진/설명 유지, 2층 장소 2개 불변, 겹침·범위 초과·실제 다른 층 수정은 거절.
- [ ] 수정 후 원래 초안을 복원해 실제 저장·재조회로 배치도 완료를 확인. 그 전에는 설정 완료로 표시하지 않음.

완료 조건: 사장님이 새 테이블을 여러 번 조정해도 같은 층에서 저장되며, 다른 층의 공간·사진·기존 참조는 변하지 않는다. 좌석 수는 설정된 수용 인원이며 실시간 착석 인원이 아니다.
