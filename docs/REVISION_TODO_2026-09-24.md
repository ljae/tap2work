## 0. 구현 전 확인할 내용

### 사용자 추가 답변 — 확정

1. **Todo는 3단계 구조로 확정.** 첫 화면은 BIG TAP별 열에 Tap 카드 → BIG TAP 열기 시 `할일 / 주문처리중 / 완료` → Tap 열기 시 Small Tap 목록 + 매뉴얼. 사용자가 BIG TAP에 **주문처리** 그룹을 추가했다. 뼈찜 조리·뼈짬뽕 조리 그룹의 Tap은 준비 작업 위주로 구성한다.
2. **Tap 완료 시 Small Tap도 모두 완료로 확정.** 직접 완료 버튼과 완료 열로 드래그하는 동작 모두 같은 일괄 완료 규칙을 사용한다.
3. **출퇴근 기록과 급여 자동 계산까지 포함으로 확정.** 수동 입력 전용 화면으로 범위를 줄이지 않는다. 계산에 필요한 지급 주기·휴게·수당·반올림 등 매장별 규칙은 별도로 설정/확정할 항목이다.

### 추가 구현 가정 — 모두 proposed

- 하단에서 빠지는 재고/발주는 Status의 분명한 진입 버튼으로 연결한다. Todo의 재고 수량 확인도 유지한다.
- Small Tap 본문 선택은 매뉴얼 열기, 체크 버튼은 완료/되돌리기다. 체크할 때에도 해당 매뉴얼을 선택해 보여준다. 매뉴얼을 읽었다는 이유로 완료 처리하지 않는다.
- 좁은 폰에서는 Small Tap 목록과 매뉴얼을 위아래로 배치하고 넓은 화면에서는 좌우로 배치한다. 양쪽 폭을 억지로 줄이지 않는다.
- 요청한 7개 BIG TAP 그룹을 새 샘플의 기본으로 제공하고 기존 사용자 폴더는 보존한다. 그룹 추가·이름 변경·정렬은 기존 편집 권한을 따른다.
- Calendar 기본은 일간 시간표, 주간 보기와 날짜 선택을 보조로 둔다. 5분 표시 단위는 기존 계획 방향을 재사용한다.
- 격자 한 칸의 실제 cm/m 크기는 미정이다. 화면의 셀 픽셀 크기와 저장 좌표를 구분하고 실측 단위를 임의로 정하지 않는다.

## 3. 작업 B — Todo 보드 데이터와 이동 API

수정 중심: `developer/operations.mjs`, `developer/checklists.mjs`, `app/lib/state/operations_controller.dart`, `app/lib/domain/checklist_draft.dart`.

- [ ] 기존 `checklistFolders → taskTemplates/tasks → steps` ID 관계를 유지하면서 BIG TAP / Tap / Small Tap에 대응시킨다. 템플릿과 당일 실행 기록을 구분한다.
- [ ] Tap 실행 기록에 저장하는 명시적 상태를 추가한다. 내부 값 제안: `todo`, `processing`, `done`; 표시명은 정확히 `할일`, `주문처리중`, `완료`.
- [ ] Small Tap 체크 개수만으로 `processing`을 재계산하지 않는다. 상태 이동과 개별 실행 기록은 완료 정책에 따라 서버에서 함께 검증한다.
- [ ] `position` 또는 명시적 순서 목록을 저장한다. BIG TAP 순서, 그룹 안 Tap 순서, 상태 열 안 Tap 순서, Tap 안 Small Tap 순서를 구분한다.
- [ ] 보드의 상태/당일 순서 변경은 해당 실행에 적용한다. 반복 템플릿 구조 변경은 관리자 편집 동작으로 구분한다. 이 적용 범위는 제안이며 UI에 명확하게 표시한다.
- [ ] `#view()`가 새로 저장한 실행별 위치를 템플릿 값으로 덮어쓰지 않도록 우선순위를 수정한다. 새 일자의 작업에는 템플릿 기본값을 사용한다.
- [ ] 새 action 예시: `move_tap`, `set_tap_status`, `reorder_small_taps`. 현재 `/api/operations`의 action 계약과 revision 검사 방식을 재사용한다. API 이름은 구현 제안이다.
- [ ] 상태 전환·드래그 저장은 하나의 원자적 변경으로 처리하고 actor/time/변경 전후를 남긴다. 대상 그룹·Tap·Small Tap 존재, 권한, 날짜, revision을 서버가 검증한다.
- [ ] Tap 직접 완료와 완료 열 drop은 **모든 미완료 Small Tap + 부모 Tap을 한 트랜잭션으로 완료**한다. 이미 완료된 Small Tap의 확인자·시각은 덮어쓰지 않는다. 새로 완료된 항목에 actor/time과 `completionSource: tap_bulk` 같은 출처를 남긴다. 출처 필드명은 제안이다.
- [ ] `complete_task`의 미완료 자식 거부 규칙을 routine Tap의 일괄 완료로 변경한다. stock task는 실제 수량 입력 계약을 유지하고 이 일괄 처리에 섞지 않는다. 중복 클릭/재시도는 같은 동작 ID로 중복 이력 생성을 막고, 일부만 완료된 채 실패하지 않게 한다.
- [ ] 마지막 Small Tap 확인 시 기존 자동 완료를 유지하는 것을 제안한다. 단일 Small Tap 되돌리기는 해당 항목만 풀고 부모를 processing으로 돌린다. 일괄 완료 되돌리기는 그 이벤트로 체크한 항목만 복원하며 이전에 개별 확인한 항목은 유지하는 방식을 제안한다. 완료 이후 다른 직원이 수정했다면 자동 복원을 거부하고 최신 상태를 안내한다. undo 정책은 아직 사용자 확정이 아니다.
- [ ] 기존 기록 migration은 완료 Tap→done, 일부 체크→processing, 나머지→todo를 후보로 삼고 기존 완료자·시각·task/step ID를 보존한다. migration을 두 번 실행해도 중복 기록이 생기지 않아야 한다.
- [ ] `주문처리중`은 음식 주문 작업의 진행 열이다. 식자재 발주 `orders`의 ordered/received와 연결하지 않는다. 일반 마케팅·정비 업무도 요청한 동일 3개 상태명을 사용하되 주문 ID를 필수로 만들지 않는다.
- [ ] BIG TAP `주문처리`의 Tap은 실제 주문 수행 단위의 샘플로 구성하고 `sourceOrderId` 등 참조를 마련한다. 뼈찜 조리·뼈짬뽕 조리의 Tap은 재료 준비·전처리·소스 준비 등 준비 작업으로 구성한다. 주문 수행과 준비 작업을 같은 Tap ID로 중복 생성하지 않는다. 실제 POS 연동은 기존 미확정 사항으로 두며 이 요청만으로 자동 주문 수신을 구현하지 않는다.
- [ ] 메뉴별 Tap/Small Tap 초안과 기존 문구의 근거 충돌은 [평택 산뼈찜 메뉴 조사](SAN_BONEJJIM_TAP_RESEARCH_2026-09-24.md)를 참고한다. 후기 사례를 현재 매장의 확정 레시피·제공 규칙으로 바꾸지 않는다.

완료 기준: Tap을 이동하고 새로고침하거나 다른 데모 클라이언트로 열어도 상태/순서가 유지된다. stale revision은 409이며 다른 사람 변경을 덮어쓰지 않는다. 예전 재고 task의 실물 수량 확인은 그대로 작동한다.

## 4. 작업 C — Todo 3단계 UI

수정 중심: `app/lib/ui/tap_workspace.dart`의 `_board`, `status`, `_toggle`, `_manual`; `app/lib/ui/tap_card.dart`; 기존 `checklist_editor.dart`의 재사용 가능한 편집 동작.

- [ ] 확정된 3단계 구조를 구현한다: 그룹별 보드 → 선택 BIG TAP의 상태 보드 → 선택 Tap의 Small Tap/매뉴얼.
- [ ] BIG TAP 보드: 그룹은 `주문처리 / 마케팅 / 뼈찜 조리 / 뼈짬뽕 조리 / 응대 / 정비 / 정산` 7개다. 나열 순서는 제안이다. 이 레벨에 할일·주문처리중·완료 열을 만들지 않는다. **주문처리**는 BIG TAP 그룹 이름이고 **주문처리중**은 다음 레벨 상태 이름이다.
- [ ] `주문처리`에는 주문별 조리/출고 작업 Tap, `뼈찜 조리`와 `뼈짬뽕 조리`에는 준비 작업 Tap을 넣는다. 예시는 주문처리의 `샘플 주문 101 · 뼈찜 2인`, 뼈찜 조리의 `재료 소분 준비`다. 메뉴/레시피 수치와 조리 기준은 임의 확정하지 않는다.
- [ ] BIG TAP 열 순서를 드래그로 바꾸고 Tap 카드를 그룹 내/그룹 간 이동할 수 있게 한다. 그룹 헤더 열기는 그 그룹의 Tap 상태 보드, Tap 카드 열기는 해당 Tap의 Small Tap으로 연결한다.
- [ ] Tap 보드: 항상 `할일 / 주문처리중 / 완료` 3개 열을 표시한다. 빈 열도 유지하고 열 이름을 수정·삭제하지 못하게 한다.
- [ ] Tap 카드: 제목·담당/R&R·시간 슬롯·장소·Small Tap 진행 수를 표시한다. 다른 열로 이동, 같은 열 정렬, 직접 완료/되돌리기를 제공한다.
- [ ] Small Tap 화면: 왼쪽 단일 목록에 모든 항목을 유지한다. 체크했다고 완료 열로 이동시키지 않는다. 오른쪽에는 선택 항목의 제목·방법·팁·장소·확인자/시각을 표시한다.
- [ ] Small Tap 본문 선택과 완료 버튼 동작을 분리한다. 체크 후에도 해당 항목과 매뉴얼을 선택 상태로 유지한다. 읽기만 가능한 직원도 매뉴얼을 열 수 있다.
- [ ] Small Tap은 목록 안에서 드래그 정렬한다. 다른 Tap으로 옮기는 구조 편집은 기존 편집 흐름을 연결하고 완료 이력의 부모 관계를 임의로 바꾸지 않는다.
- [ ] 마우스는 손잡이 드래그, 터치는 길게 누르기/손잡이로 제공한다. 삽입 위치, 빈 열 drop target, 가로 자동 스크롤, 취소/실패 시 복원을 지원한다.
- [ ] 모든 드래그에 이동 메뉴·위/아래 버튼 같은 대체 수단을 제공한다. 카드 열기와 드래그가 서로 오작동하지 않게 한다.
- [ ] 정렬은 검색/필터 중 숨겨진 항목의 순서를 손상하지 않아야 한다. 첫 구현 제안: 필터 중 정렬 손잡이를 비활성화하고 필터 해제 동작을 안내한다.
- [ ] 권한 없는 완료/이동은 이유를 표시한다. polling 중 선택 ID와 스크롤을 가능한 한 유지하고 삭제된 선택은 빈 상세 안내로 전환한다.
- [ ] 공개 정적 리뷰에서는 보드 조작을 actor/day별 메모리 체험으로만 처리한다. 상태 이동·체크·되돌리기 모두 POST 0건이어야 한다. 기존 공유 데모 서버 연결 모드는 별도로 유지한다.
- [ ] breadcrumb, 현재 범위 검색, 내 담당만, 재고 확인 진입을 새 구조에 맞춘다. 기존 카드 스타일과 사용자 제공 빨간 로고를 재사용한다.

완료 기준: BIG TAP에는 그룹 열만 있고 Tap에는 정확한 3개 상태 열이 있다. Small Tap을 선택/체크하면 같은 화면의 상세가 바뀐다. 데스크톱과 폰에서 드래그 및 버튼 대체 조작이 가능하다.

### D-1. 출퇴근·휴게 기록과 급여 자동 계산 — 요청 확정

수정 제안: `app/lib/ui/attendance_panel.dart`, `app/lib/ui/payroll_panel.dart`, `app/lib/domain/attendance.dart`, `app/lib/domain/payroll.dart`, `developer/attendance.mjs`, `developer/payroll.mjs`. 새 파일명은 권장안이며 계산의 저장 결과는 서버를 기준으로 한다.

- [ ] Tapper 본인 근무 화면에 출근 / 휴게 시작 / 휴게 종료 / 퇴근을 제공하고 현재 상태·출근 시각·오늘 실근무 누적을 표시한다. 데모에서는 선택한 actor와 Tapper의 매핑을 표시한다. 실제 직원 사용에는 기존 미구현 인증/소속 확인 작업이 필요하다.
- [ ] 상태를 `off_duty → working ↔ on_break → off_duty`로 관리한다. 중복 출근, 출근 전 퇴근, 휴게 전 휴게 종료, 종료 전 새 세션 등 잘못된 전환은 서버에서 거부한다. 휴게 중 퇴근의 처리 규칙은 명시적으로 설정한다.
- [ ] 근태 이벤트에 ID, Tapper ID, 서버 시각, 종류, 기록자, 보정 참조를 저장한다. 클라이언트 시계만 신뢰하지 않는다. 요청 ID로 재전송을 중복 처리하지 않고 네트워크 실패 시 출근 성공을 표시하지 않는다.
- [ ] 미퇴근/누락 기록은 미확정으로 표시하고 관리자 보정 흐름에서 시작·종료·휴게와 사유를 입력받는다. 원본 이벤트를 지우지 않고 정정 이력을 연결한다. 자동으로 예정 퇴근 시간을 채워 확정하지 않는다.
- [ ] 실근무 시간은 유효한 출퇴근 구간에서 휴게 정책에 따른 제외 시간을 뺀 값으로 계산한다. 현재 열린 근무 구간은 진행 중 추정치로 표시하고 확정 실적과 구별한다. 자정/주/급여 기간 경계를 넘는 구간을 정확히 분할한다.
- [ ] 급여 규칙 데이터에 시급 또는 고정 기본액, 유효 시작일, 지급 주기, 기간 경계, 휴게 처리, 원 단위 반올림, 추가보수/공제 항목을 저장한다. 매장별 법정 수당 규칙은 적용 지역·조건을 공식 출처로 검증한 뒤 설정하며 배율을 하드코딩하지 않는다.
- [ ] 유효 근태가 추가/확정/정정되면 해당 기간의 급여 초안을 서버에서 재계산한다. 결과에 근태 ID/버전, 단가·규칙 버전, 기본액, 추가보수, 공제, 합계, 지급액, 잔여액의 계산 근거를 남긴다.
- [ ] 마감된 급여 기간은 새 시급이나 규칙 변경으로 과거 값이 조용히 바뀌지 않게 고정한다. 마감 후 근태 보정은 차액 조정 내역 또는 명시적인 재마감 동작으로 처리하는 방식을 제안한다.
- [ ] 계획 근무 기반 예상 급여, 근태 기반 누적 급여, 마감 금액, 실제 지급 기록을 구분해 표시한다. 월급 고정액의 결근/중도입사 일할 계산 등은 규칙 미설정 시 계산 불가/확인 필요로 표시하고 임의 공식으로 채우지 않는다.
- [ ] 지급 등록에는 날짜·금액·대상 기간·기록자를 남긴다. 자동 급여 계산 요청은 실제 계좌 이체 연동을 포함하지 않는다. 지급 기록 수정은 기존 기록의 정정으로 남긴다.
- [ ] 가상 직원 09:00 출근→12:00 휴게→12:30 재개→18:00 퇴근은 무급 휴게 30분 설정에서 8.5시간이다. 테스트 단가 10,000원, 추가보수 5,000원, 공제 없음이면 90,000원; 40,000원 지급 기록 후 잔여 50,000원이어야 한다. 이 숫자는 계산 테스트용이며 실제 급여 기준이 아니다.

완료 기준: 실제 출퇴근 버튼으로 만든 가상 근태가 Team 주간 실적과 급여 초안에 연결된다. 중복 요청, 누락 퇴근, 휴게, 자정 넘김, 단가 변경, 보정·마감·부분 지급을 검증한다. 화면에 자동 계산 합계만 넣고 근태 이벤트/근거를 생략한 구현은 완료가 아니다.

## 6. 작업 E — Calendar / Tap 시간과 R&R 근무 흐름

수정 중심: 새 `app/lib/ui/calendar_screen.dart`, `app/lib/domain/tap_planning.dart`, `tap_workspace.dart`의 `_timeline`, 직원·근무 서버 모듈.

- [ ] 근무 밖 Tap은 운영상 초과 배정 표시로 표현한다. 확정 근태나 급여 수당으로 자동 변환하지 않는다.

완료 기준: 한 날짜에서 R&R별로 누가 언제 근무하며 어느 Tap을 수행할 예정인지 읽을 수 있다. Calendar와 Team이 같은 근무 데이터를 사용하고 Todo와 같은 Tap ID/상태를 사용한다.
