# 매뉴얼 고도화 · 한 항목씩 미리 보고 결정하기

2026-10-10. 사용자 요청: 주요 내용을 하나씩 검증하고, 명확해야 할 부분을 빠르고 적은 비용으로 미리 보며 결정한다.

## 진행 방식

한 회차는 **한 가지 결정 → 비교 가능한 작은 시안 → 직접 체험 → 질문 하나 → 답변 반영**이다. 한 번에 전체 기능을 구현하지 않고, 기존 초안·HTML·정지 그림·간단한 모션으로 행동을 먼저 검증한다. 새로운 이미지/영상 생성·유료 서비스·앱 전체 빌드는 필요한 결정에만 사용한다. 확정한 C01–C12는 다시 묻지 않는다.

각 시안은 가상 매장과 체험 상태로 구성한다. 시안 선택 자체는 서버 저장·실제 업무 완료·제품 구현 완료가 아니다. 사용자의 답변을 결정 이력에 반영한 뒤 필요한 앱/데이터 변경 범위를 좁힌다. 추정 사용성 점수나 현장 검증 결과를 만들지 않는다.

## 회차 01 · A안 확정

A: 별도 웰컴. 첫 근무와 중요 변경 시 내용을 집중해 보여주고 확인 또는 바로 업무 보기로 이동한다.

B: 업무 위 카드. 오늘 할 일과 같은 화면에서 분위기·원칙을 펼쳐 보고 확인한다.

두 안 모두 확인하지 않아도 업무를 볼 수 있고, 업무 ON은 별도다. 다음 근무에는 확인한 웰컴을 다시 펼쳐 볼 수 있다. 웰컴 확인·안내 시작은 실제 수행 체크를 늘리지 않는다.

사용자 답변: **A · 별도 웰컴 화면**. 첫 근무·중요 변경 시 별도 화면, 평소 다시보기로 구성한다. 화면의 상세 문구·핵심 정보는 다음 본보기 검토에서 보완할 수 있다. B안은 비교 기록으로 보존한다.

시안은 `docs/prototypes/manual-navigation-review.html`. 의존성 설치 없이 기존 Pretendard 파일과 함께 로컬에서 제공한다. 사용자는 실제 화면을 본 뒤 선택하거나 문구·내용을 수정할 수 있다. 비교를 위한 HTML이며 Flutter 화면 구현은 아니다.

실제 검사 결과와 사용자 선택은 canonical history에 기록한다. 다음 회차는 이번 선택·수정 사항을 반영한 뒤 준비한다.

- A/B 데스크톱 캡처 시각 검토. 캡처와 제공 사본은 `.local/manual-navigation-review/`, 브라우저는 사용자에게 제어를 넘겼다.
- 로컬 제공 주소 `http://127.0.0.1:8767/`. 원본 HTML·기존 글꼴만 제공한다. 새로고침 시 체험 상태 초기화.
- 첫 로컬 서버/브라우저 실행은 sandbox 제한으로 실패했고 승인된 외부 실행으로 검증했다. 앱/서버 API·공용 DB·콘텐츠 발행·외부 배포는 수행하지 않았다.

## 회차 02 · 최초 A/B 비교 (아래 사용자 수정으로 대체)

[세척 구역 준비 시안](prototypes/manual-task-review.html). A는 핵심 행동3개를 각각 체크하고 B는 같은 행동 목록을 참고한 뒤 업무 전체를1회 체크한다. 두 안의 상세 설명은 동일하다. 모든 설명 문장에 체크를 붙이는 안은 아니다.

상세는 바로 할 행동→준비물·방법·예시→이유·실수 예시/완료 기준·모르면 할 일로 펼쳐 본다. 위치는 가상 구역을 표기한 도식이며 실제 장비·제품 수치를 만들지 않았다. 실제 내용의 현장 검수는 별도다.

이번 시안은 일반 업무 본인 체크만 비교한다. 기존 핵심 업무 버디 확인/부재 사유 정책은04회차에서 검토한다. 설명 열기·돌아오기는 수행 체크를 만들지 않고, 체크는 되돌릴 수 있다. 변형 전환/다시 체험은 이 화면의 상태를 초기화한다.

질문 하나: 신입의 이 업무는 핵심 행동3개로 확인할까(A), 전체 준비 완료1개로 확인할까(B)? A의 체크들은 같은 TAP의 Task에 해당하는 제안이며 담당을 Task별로 나누는 뜻이 아니다. 선택 전 현재 제품 계약으로 확정하지 않는다.

제공 주소: `http://127.0.0.1:8767/review-02.html`. 기존 style과 Pretendard를 재사용했다. 이전 시안은 `/review-01.html`에서 계속 확인할 수 있다.

검증: 실제 브라우저 클릭으로 읽기만으로 체크0 유지, 상세 왕복 후1/3 유지, A3/3 완료와 되돌리기, B 읽기/1회 완료/되돌리기 통과. 320/390/1200px 가로 넘침 없음·보이는 버튼 최소48px. 390px 상세 화면의 본문/보조 글자1.5배 근사 검사에서 넘침 없음. 업무 목록·상세 데스크톱 캡처를 시각 검토했다. HTML 체험 결과이며 Flutter/실매장/백엔드 검증이 아니다. Ego space6을 사용자에게 다시 넘겼다.

## 회차 02 · 사용자 수정: 체크리스트와 매뉴얼을 한몸으로

사용자 명시 요구: **핵심 행동·자세한 설명·사진 링크·수행 체크를 한 화면에 담고 좌우 슬라이드로 다음 행동을 본다.** 별도 방법 화면을 오가는 최초 A/B안보다 이 요청을 우선한다. 사진 첨부와 접시 종류·잔반 배출 장소·배수구 막힘 예방 내용도 포함한다.

[통합 슬라이드 시안](prototypes/manual-action-slides-review.html)은 4장으로 구성했다. 이는 해당 본보기의 구체안이며 모든 업무를4단계로 고정하지 않는다.

| 행동 | 같은 화면에 보이는 내용 | 연결할 실제 매장 사진 |
|---|---|---|
| 1 남은 음식 먼저 비우기 | 고형 잔반, 뼈/껍데기/휴지 등 분리 기준, 국물·기름의 지정 수거 위치 | 음식물통·별도 분리통·액체/기름 수거 위치 |
| 2 반납 식기 분류 | 큰 접시/앞접시, 밥/국그릇, 컵/수저의 반납 자리; 냄비·깨진 식기의 별도 확인 | 반납대의 종류별 자리와 표시 |
| 3 거름망·배수 확인 | 거름망 위치·고형물 수거·느린 배수/역류 보고, 배관 임의 분해 금지 | 세척용 싱크대와 거름망, 손 씻는 세면대와 용도 구별 |
| 4 깨끗한 식기 건조 | 세척·소독을 마친 식기만 종류별 건조 자리, 젖은 식기를 임의로 포개지 않기 | 접시/그릇/컵/수저의 건조 위치·랙 |

각 장에는 행동 제목·사진/위치 도식·3개 설명·주의·완료 기준·수행 체크가 함께 있다. 글자 확대나 긴 내용은 같은 장 안에서 세로 스크롤하고 체크/이전/다음은 하단에 유지한다. 좌우 넘기기는 완료를 만들지 않는다. 최신 사용자 수정으로 **완료 체크 시 다음 행동으로 자동 이동**한다. 체크 없이 좌우 탐색도 가능하며 탐색은 완료를 만들지 않는다. 마지막 행동은 현재 장에서 완료 상태를 표시하고, 완료 체크 되돌리기는 이동하지 않는다. 앞선 체크/넘기기 별도 조작 답변은 이번 수정으로 대체한다.

시안의 파일 첨부는 선택한 이미지의 브라우저 임시URL로 현재 행동에만 표시하고 서버에 업로드하지 않는다. HTTPS 사진 링크도 현재 행동별로 연결하고 확대할 수 있다. 실제 매장 사진은 제공받지 않았으므로 기본 표시는 ‘실제 사진 미등록’ 위치 도식이다. 임시8MB 제한은 시안용이며 현재 앱의 장소사진350KB 계약을 변경하지 않는다. 생산 사진 업로드/저장/권한 정책은 구현 전 별도 계약으로 정한다.

후속 사진 요구로 위의 원본 파일 표시/임시8MB 정책은 아래 촬영·자동 최적화 시안으로 대체했다. 실제 앱의 기존350KB 장소사진 계약은 아직 그대로다.

위치·폐기물 분류·식기 배치·장비 지침은 매장 확인값이다. 예시를 한국 법정 분류나 실제 매장 기준으로 단정하지 않는다. 배수 관련 일반 구조 참고로 [NYC DEP의 사업장 기름 배출 안내](https://www.nyc.gov/site/dep/water/disposing-of-grease-as-a-business.page)를2026-10-10 열람했다. 지방/기름의 하수 배출과 막힘 관계를 참고한 것이며 뉴욕 설비·법률을 국내 의무로 제시하지 않는다. 수거함 위치·국물 처리·거름망 안전 수거 방법은 매장에서 확정해야 한다.

제공 주소: `http://127.0.0.1:8767/review-02-slides.html`. 통합 슬라이드 방향은 사용자 지시로 확정이고 실제 앱 구현·콘텐츠 발행은 아직이다. 반납 식기 처리/건조를 보여주는 시나리오이지 첫 오픈 준비만을 뜻하지 않는다. 실제 체크 반복 빈도·발생 시점과 모든 접시마다 체크할지 여부는03회차에서 결정한다.

## 사진 후속 · 바로 촬영·업로드 전 자동 최적화

사용자 확정 요구: 고화질 원본 저장 대신 필요한 화질로 변환한 뒤 업로드해 스토리지 부담을 줄인다. 휴대폰에서 바로 사진을 찍어 등록하는 흐름을 우선한다. 원본 보관은 기본으로 하지 않는다.

검토 시안은 후면 카메라 요청 버튼과 별도 앨범 선택을 제공한다. 선택한 파일을 디코드하고 Canvas로 크기를 줄여 JPEG로 다시 인코딩한다. 회전 정보를 반영한 디코드를 요청하며 원본 파일 대신 새 픽셀 인코딩 결과를 체험 화면에 표시한다. 동일 행동의 오래된 변환 결과가 새 파일/사진 삭제를 덮어쓰지 않도록 작업 번호와 행동 ID를 고정한다.

초기 기술 기준은 **proposed**다. 긴 변1280px(작은 사진 확대 안 함), JPEG 품질0.76부터 단계 조정, 목표150,000바이트/상한250,000바이트. 필요 시1024/800px와 품질0.68/0.60을 검토하며 조건을 충족하지 못하면 원본을 올리지 않고 재촬영 안내한다. 글자/라벨을 읽는 데 충분한지는 실제 매장 사진으로 검토해야 하고 ‘최적’ 화질 검증 완료를 의미하지 않는다. 작은 썸네일과 원본 미보관·변환본만 Storage 저장은 생산 구현안이다.

실제 앱은 현재 파일 선택 후350KB 초과를 거절하고 `zones.photo`에 dataURL/HTTPS를 저장한다. 자동 촬영/변환·전용 Storage 업로드는 미구현이다. 생산 구현에는 공통 사진 처리기(촬영→방향/크기/인코딩→미리보기→매장 권한 검증→업로드→사진 참조 CAS 저장), 실패·재시도/취소, 고아 업로드 정리, 참조 중인 과거 사진 보존과 구dataURL 호환을 포함한다. DB/매장 상태에는 사진 바이트 대신 경로·크기·포맷·버전 참조를 두는 안을 제안한다. 카메라 취소/권한 거절에는 앨범 대안을 유지한다.

브라우저 검증: 합성3200×2400 라벨 이미지→1280×960 JPEG13,960바이트; 복잡한 합성2400×1600 이미지→800×533/164,897바이트; 작은100×80 이미지 확대 없음; 손상 파일 거절. 실제 파일 선택 경로에서는 검토 화면 PNG178KB→JPEG100KB로 변환·표시하고 테스트 사진을 제거했다. 후면 카메라 요청속성 `capture=environment` 확인. 실제 촬영·HEIC·EXIF 회전/GPS 원본 검증·운영 Storage 업로드는 미실시다.

기술 문서2026-10-10 확인: [카메라 capture 요청과 브라우저 차이](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture), [Canvas JPEG 변환](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob). 데스크톱에서는 파일 선택으로 동작할 수 있어 촬영 흐름은 실제 Android/iPhone 검증 후 제공 범위를 정한다.
