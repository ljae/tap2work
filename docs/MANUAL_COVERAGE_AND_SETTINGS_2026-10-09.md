# 외식업 매뉴얼 범위·설정 연결·매장 수정 표시

상태: 사용자 요구는 확정, 아래 분류·연결 계약·시각 세부안은 proposed. 앱/DB 구현이나 공용 매뉴얼 발행 완료를 뜻하지 않는다. [앞선 조사](MANUAL_STRUCTURE_RESEARCH_2026-10-09.md)의 원본 사본/연결·업데이트 정책 미정 상태를 유지한다.

사용자 요구: 일반적인 식당에서 업무 종류를 새로 설계해야 하는 부담을 없앨 만큼 매뉴얼 소스를 조사한다. 개별 매장 조정은 허용한다. 매뉴얼 구성 조건과 기존 설정을 연결해 재입력을 줄이고, 매장용으로 수정된 매뉴얼·업무리스트를 색·아이콘으로 구별한다.

일반적인 한식당·고깃집·분식·치킨·중식·일식·카페·제과·주점·포장 전문점을 대조 사례로 삼는다. 서비스 방식·설비·공정·판매 메뉴가 달라져도 업무 목적은 이 영역에 매핑하고 조건부 절차를 추가한다. 새 업무 추가 기능은 예외용으로 남긴다. 채용·급여 계산·교육 평가·창업 부동산 검토를 이번 일상 운영 범위에 끼워 넣지 않는다.

### 완성 판정

- 매장 사례별 시작→영업→교대→마감, 납품·고장 등 사건, 정기 관리까지 대조해 누락 업무를 기록한다.
- 각 업무에 출처/검토일/적용 대상, 방법, 완료 상태, 이상 시 행동, 매장 입력, 확인 방식, 실행 조건이 있어야 한다.
- 동일 대상·목적·실행 시점의 중복 확인은 합친다. 방법 문서 공유와 실행 합치기는 다르다. 주간 정비를 일일 마감 완료로 대체하지 않는다.
- 대표 사례에서 새 **업무 영역**이 필요하면 분류를 보완한다. 매장별 항목 추가·수정은 정상적 사용이다.
- 현재 91개 로컬 후보에는 다른 산업/법무 내용도 포함되므로 '식당 매뉴얼91개 완비'라고 표시하지 않는다. 현재 목록에 화장실·장비별 정비·회수 등이 제목 단위로 독립되어 있지 않은 것은 확인했으나 본문에 전혀 없다는 전수 판정은 하지 않았다.
- 현장 사용성 및 누락률은 아직 미측정. 실제 매장 시나리오 검토와 절차 원문 작성·검토가 남아 있다.

## 한 번 입력하고 연결하는 설정 계약

기존 원본을 우선 사용한다. 조건 연결을 위한 신규 필드 명칭은 제안이며 기존 API에 이미 존재한다고 주장하지 않는다.

| 단일 원본 | 최초/후속 편집 진입 | 저장 동작 | 소비하는 화면·내용 |
| --- | --- | --- | --- |
| store.profile.businessTypeId / serviceModes | 업종·운영 형태 | 기존 매장 프로필 저장 + 구성 변경 영향 계산(신규) | 기본 추천, 홀·포장·배달 절차 |
| workplace.days / breaks | 공통 영업시간 편집 | 기존 영업시간 저장 | 근무표, 시작/마감/브레이크 기준 업무 |
| workplace.parts / 권한 데이터 | 공통 파트·직책 편집 | 기존 분류·권한 저장 | 담당 파트 추천/업무 접근. 파트로 권한 판단 금지 |
| layout / zones | 배치도 또는 공통 공간·장비 편집 | 기존 zone ID 재사용, 의미 타입/운영 상태 확장(신규) | 장비 청소·점검·시설 종료·물품 위치 |
| sales.menus / items / 재료 연결 | 기존 메뉴·품목 편집 | 기존 편집 액션 | 메뉴별 준비·조리, 품목·보관 연결 |
| 매장 운영 조건(신규) | 셀프바 등 관련 질문, 같은 편집 시트 | 조건 ID별 yes/no/unknown 저장 | 조건부 절차 포함/제외 |
| 매장 공통 값(신규) | 매뉴얼의 미입력 값에서도 같은 시트 | 배출 장소·비품 위치·연락 담당 등 ID 참조 | 모든 관련 매뉴얼에 같은 값 표시 |
| 업무 계획 | 업무 연결 설정 | 기준 사건 + 상대 시간 또는 명시 시각 | 실제 업무 생성·담당·반복 |

시설은 배치도 좌표를 그리지 않아도 먼저 등록 가능하게 설계한다. 후에 배치도에 배치할 때 같은 ID를 사용한다. 현재 zones.kind=equipment만으로 냉장고/화구를 판별할 수 없으므로 이름 추측으로 자동 확정하지 않는다. 셀프바라는 운영 기능과 실제 셀프바 위치는 각각 조건/장소 역할로 연결한다.

공통 값은 값의 복사 대신 참조로 표시한다. 예: `배출 장소 · 건물 뒤 지정 구역 · 매장 정보에서 연결` → 누르면 동일 편집 시트. 저장 전 `홀 마감·주방 마감에서 함께 사용`을 보여준다. 특정 매뉴얼만 다른 값이 필요하면 명시적으로 `이 업무만 다르게`를 선택하고 별도 값임을 표시한다. 일반 입력마다 두 번 저장시키지 않는다.

영업 종료23:00 → 23:30 변경 시 `종료 후30분` 업무는00:00으로 재계산하되 고정23:10 업무는 유지하고 영향 목록에 구별한다. 한국 영업일·야간 경계를 유지한다. 완료/진행 업무는 기준 snapshot을 보존하는 방향이며 진행중 변경 정책은 별도 합의한다. D-017 발주 후N일·주문당1회 재고 확인 규칙을 반복 청소 주기로 바꾸지 않는다.

### 조건 변경의 저장 흐름

1. 초안에서 조건 변경 → 필요한 업무/입력/순서 변경만 계산한다.
2. 기존 수정과 연결되는 항목을 ID로 매칭한다. 업종 재선택이 곧 전체 재설정은 아니다.
3. 같은 시트에 `추가될 절차 / 앞으로 제외될 절차 / 유지되는 매장 수정 / 새로 필요한 입력`을 보여준다.
4. 최종 저장1회로 조건·구성·변경 이력을 일관되게 반영한다. CAS 충돌은 최신 상태와 비교하며 실패하면 초안을 보존한다.
5. 제외된 조건의 수정값·사진·과거 실행은 보관한다. 다시 활성화하면 기존 값을 제시한다. 이미 완료된 기록을 다시 구성하지 않는다.

이 흐름은 매장 조건 변경에 대한 제안이다. 플랫폼 공통 원본 업데이트의 자동/확인 후 반영 정책은 별도 미정이다. 재고·메뉴·장비를 추가했다는 이유만으로 검토 전 업무를 즉시 활성화하지 않는다.

## 수정 표시: 출처와 상태를 분리한다

업종/공통은 추천 이유, 매장 수정은 변경 상태다. 서로 배타적인 폴더나 분류로 만들지 않는다.

| 상태 | 문구·아이콘 | 색/노출 |
| --- | --- | --- |
| 기본 절차 유지 | 문서 아이콘 + 기본 제공 | 상세에서 muted, 목록에 모든 기본 배지를 반복하지 않음 |
| 공통 매장 정보만 입력 | 연결 아이콘 + 매장 정보 연결 | 값 옆 muted. 직접 절차 수정으로 집계하지 않음 |
| 내용·기준·순서·포함 항목 수정 | 연필 아이콘 + 우리 매장 수정 | 기존 coral #FF9986 / accentSoft #392622 배지, 매뉴얼과 업무 카드에 동일 |
| 직접 새 항목/업무 작성 | 더하기 문서 아이콘 + 직접 추가 | 같은 coral 계열, 문구·아이콘으로 구별 |
| 입력이 남음 | 정보 아이콘 + 설정 필요 | 기존 amber. 위 수정 상태와 별개 |

완료·선택의 초록색을 매장 수정에 사용하지 않는다. 코랄은 수정/추가, 경고는 별도 amber. 배경 전체를 물들이지 않고 작은 배지를 사용한다. 색 없이도 읽히는 문자·아이콘 및 접근성 이름을 함께 제공한다. 아이콘만 작은 터치 타겟으로 만들지 않고 카드 상세에서 수정 내용을 확인한다.

- 매뉴얼 목록: 제목 아래 `연필 우리 매장 수정` 배지. 펼치면 바뀐 항목·설정과 기본 기준 비교.
- 오늘 업무: 실행 생성 시점의 수정 상태를 같은 배지로 표시. 현재 매뉴얼이 나중에 바뀌었다고 과거 업무 배지가 변하지 않음.
- 상세 항목: 실제 수정된 항목에만 연필 표시. 일반 조건 조합/장소 입력 자체는 매뉴얼을 전부 수정 상태로 만들지 않음.
- `원래대로`는 절차 변경과 매장 공통 값을 구분하며 공통 입력값을 삭제하지 않음. 복원 전 달라질 내용을 보여주는 방향.
- 기존 catalogLinks.mode=personalized는 업종 변형·복원에도 사용되므로 그대로 '사장님 수정'으로 번역하지 않는다. originKind, 구성 버전, 실제 변경 상태를 분리해야 함. 원본 없음/legacy 불명은 '직접 추가'로 추정하지 않는다.

## 확인 가능한 UI 시나리오

[검토용 화면](prototypes/manual-setup-review.html)은 실제 앱이 아닌 독립 인터랙션 시안이다. `셀프바 운영 → 구성 변경 검토 → 적용`과 `배출 장소 저장 → 모든 연결 값 반영`, `앞치마 수거 추가 → 매뉴얼/오늘 업무 수정 배지`를 시연한다. 브라우저 메모리만 사용하며 다시 열면 초기화된다. 실행 기록 snapshot·서버 권한/CAS·원본 갱신을 구현한 시안은 아니다.

다음 실제 구현은 조건/공통 값 계약 및 원본 정책 확정 → 서버 구성/변경분 모델 → 공통 설정 연결 → Flutter 배지·설정 UI → 카탈로그 재구성/발행 검토 순서로 나눈다. 이번 문서가 원본 연결 방식을 승인하거나 운영 DB를 초기화하지 않는다.
