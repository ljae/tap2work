# Restaurant operations scenario review · 2026-09-25

Astra reviewed the Flutter application and operations store against `PRODUCT.md` and canonical project state revision 50. This is a code-grounded review of the existing restaurant demo, with isolated temporary-store reproductions. It is not a live restaurant trial, a production readiness certification, or CEO feedback. The scenarios below use fictional workers and orders.

The system supports a useful daily coordination loop: prepare the store, work through order-specific menu TAPs, track prepared portions separately from purchased ingredients, count/order/receive materials, and plan qualified staff. The review reproduced three implementation defects under existing decisions. The fixes and verification are recorded below; the reproductions remain as evidence of the pre-fix behavior.

## Confirmed findings and exact reproductions before the fixes

Line references below refer to source inspected before fixes and may move when implementation is applied.

### F1 · compensation amount disclosed to non-owners through activity

Priority: high within this demo's existing role boundary. `developer/staff.mjs:187–196` records an owner payment/adjustment and logs the amount as a plain shared activity message. `developer/operations.mjs:166` clones state into a role response; pay fields are projected through `staffView`, but activity is retained. `app/lib/ui/operations_screen.dart:418` renders recent activity.

Reproduction executed against a temporary JSON store with clock `2026-09-25T03:00:00Z`:

1. `snapshot('owner')` obtains the current revision.
2. `mutate('owner', { action: 'record_payment', tapperId: 'tapper-crew', amountWon: 123456, date: '2026-09-25', revision })`.
3. `snapshot('crew')` returns `payRecords: []` and `activity[0].message: "급여 지급 기록 123456원"`.

Expected: full amount-bearing history remains available to owner; no compensation amount in manager/cook/crew responses, including legacy untagged events. Suggested correction: structured audience metadata for new events plus conservative projection for already stored pay-event messages. Regression should inspect the entire response, not merely `payRecords` and `hourlyWon`.

### F2 · obsolete preparation completion adds nonexistent output

Priority: high for stock integrity. `developer/prepared_items.mjs:39–44` supersedes unnecessary open work after an increased physical count. `developer/operations.mjs:230–237` accepts `complete_preparation` without checking `supersededAt`; `move_tap` and several adjacent task mutations also lack the same lifecycle guard.

Executed reproduction:

1. Obtain one generated preparation TAP and its prepared item ID from fresh snapshot.
2. Submit `count_prepared_item` with quantity `20`, reason `review reproduction`, current revision.
3. Confirm old preparation TAP is no longer in response.
4. Submit `complete_preparation` with the old TAP ID, quantity `10` and the **new current revision**.
5. Actual: accepted, on-hand becomes `30`.

Expected: reject obsolete task and leave balance `20`, movements and evidence unchanged. Test current revision deliberately so failure cannot be attributed only to a stale version. Also test completing the final Small TAP, moving/reopening and manual/reorder paths consistently. A newly generated valid preparation must still be completable.

### F3 · order Small TAP ordering is discarded despite save success

Priority: moderate workflow correctness. `developer/operations.mjs:343–348` sorts by submitted Small TAP IDs. `developer/order_taps.mjs:54–57` unconditionally sorts an existing unfinished order back into default channel order during `ensureDueTasks`, which runs at the end of the same mutation.

Executed reproduction:

1. Choose active order menu with `order-check`, `cook-check`, `pack-check`, `handoff`.
2. Submit `reorder_small_taps` with reversed IDs and current revision.
3. Actual success response already returns `[order-check, cook-check, pack-check, handoff]`.

Expected: returned response and later snapshots preserve submitted sequence. New and migrated channel steps still receive sensible default order; completed evidence remains intact. Limit canonical ordering to creation or genuine migration, or explicitly preserve a customized sequence marker. Test successive snapshots and a later completion mutation as well as initial save.

## Fixes applied after the review

Sol implemented and tested the focused corrections without changing product decisions:

- **F1:** New pay activity carries an owner-only kind. Non-owner server projections remove that activity and legacy amount-bearing pay messages; the owner retains the full audit. A regression checks owner, manager, cook and crew after both a payment and adjustment.
- **F2:** Superseded preparation work rejects completion, Small TAP completion, movement, manual edits, reorder and reopening. Rejected actions leave stock, movements and revision unchanged. The public preview also refuses a superseded completion.
- **F3:** Saving a Small TAP sequence persists through snapshots and store reload. A newly introduced packing step is inserted before handoff during migration without sorting existing steps.
- **Preview parity:** A generated preparation TAP now uses the same `max(batchQuantity, target − onHand)` planning rule as the server.

After these changes: 54/54 Node console tests, 80/80 Flutter tests, Flutter analysis, JavaScript checks, public review build and `git diff --check` passed. No native build, physical-device test, authenticated live mutation or deployment was performed for this review.

## Remaining gaps and proposed work

- Legacy leave/cover offers do not update the structured calendar. A unified dated absence/coverage flow needs design, including qualification and overlap checks during acceptance.
- Raw procurement lacks partial receipt/cancellation/substitution and supplier integration. Prepared outputs do not automatically consume raw recipe inputs or model waste, expiry lots or yield. These are distinct future workflows, not grounds to merge the two balances.
- Synthetic ticket creation is not a production POS intake API. Restaurant cancellation/refund/amendment and prepared-usage compensation need explicit transition rules before live integration.
- Routine task midnight reset does not provide overdue handover, assignment escalation or production notifications. A restaurant closing after midnight may need a business-day boundary decision; the implemented boundary remains Korean calendar midnight.
- Pay correction sequencing and legally compliant pay computation are not verified here. Existing estimates are demo calculations; do not infer production payroll support from displayed amounts.
- Physical phone testing remains necessary for touch drag, floating-menu reach, long Korean text and noisy/poor-connectivity kitchen use. Existing responsive Flutter tests are useful but do not establish real-world usability.

None of these proposals changes a confirmed decision. No supplier orders, employee messages, live mutations or new user feedback were created in this review.
