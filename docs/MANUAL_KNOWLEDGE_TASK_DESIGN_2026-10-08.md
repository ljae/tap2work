# 매뉴얼 분류·업무 연결·레시피 지식 설계

작성 2026-10-08. **상태: 조사 및 구현 가능한 설계안(proposed). 앱/DB/공용 카탈로그에는 아직 적용하지 않음.**

사용자 확정 요구: 브레이크타임을 업종 공통으로 다루고 특정 메뉴 내용을 분리한다. 매뉴얼과 할 일의 연결 공백을 점검하면서 설정·체크 부담을 줄인다. 기본 레시피와 보관·준비·품질 노하우를 근거와 함께 축적하고 업데이트한다. 아래 분류 필드, 화면 구성, 실행 방식은 이 요구에 대한 제안이다. 기존 D-073의 TAP 단위 운영 설정, D-081의 개인화 보호, D-103의 업종 기본 묶음을 보존한다.

브레이크가 UI에서 공통처럼 보인 정확한 경로는 해당 운영 매장 화면/발행본 미조회로 미확정이다. 원본에서는 bonejjim에 속하므로 collectionId가 common으로 잘못 저장됐다고 단정하지 않는다. 그러나 공통 TAP 부재와 혼합된 내용은 소스로 재현했다.

## 3. 분류: 한 폴더에 모든 의미를 맡기지 않는다

매뉴얼의 기본 탐색은 **운영 / 위생·보관 / 메뉴·레시피 / 장비·시설 / 응대·인계**로 제안한다. 기존 purposeId는 삭제하지 않고 이 화면 분류에 매핑한다. 기존 사용자 그룹도 자동 이동하지 않는다. 오픈·브레이크·마감은 폴더 계층이 아니라 시간대 필터이며, 업종은 적용 조건이다. 검색 결과는 동일 지식 ID를 한 번만 보여준다.

| 분류 축 | 예 | 저장/사용 원칙 |
|---|---|---|
| 적용 범위 | 전 업종 공통 / 외식 공통 / 공정 공통 / 특정 메뉴·재료 / 매장 전용 | scope enum. common이라는 이름만으로 전 업종에 추천하지 않음 |
| 주제 | 냉각, 해동, 튀김, 영업중단 안내 | 재사용할 processIds. 치킨/돈까스에서 같은 튀김 공정 원본 참조 |
| 적용 조건 | 국물 제조 여부, 셀프바, 냉동떡 취급, 브레이크 운영일 | 구조화된 applicability. 조건 모름은 ‘확인 필요’, 일치로 간주하지 않음 |
| 찾는 시점 | 오픈 / 준비 / 영업중 / 브레이크 / 마감 / 필요할 때 | phaseIds는 검색용. 실행 시각은 실제 매장 시간표로 별도 결정 |
| 대상 연결 | 메뉴ID, 재료/제품ID, 장비유형 | 이름 문자열 추론 대신 ID. 매장에 없는 대상은 추천 제외 |
| 지식 성격 | 절차 / 레시피 / 보관법 / 품질 팁 / 문제 해결 / 법적 기준 | 정보의 형식. 체크 여부와 독립 |

공용 원본에는 매장 고정 시각, 특정 브랜드 메뉴명, 실제 파트/크루 ID를 넣지 않는다. 공통 원칙을 복제해 업종별 버전을 양산하지 않고, 업종별 묶음은 지식 ID 목록과 필요한 차이만 참조한다. 안전 조건의 충돌은 ‘더 구체적인 내용이 항상 우선’으로 해결하지 않고 검토 대상으로 반환한다.

## 4. 브레이크타임 분리안

| 새 지식/TAP 후보 ID | 내용 | 적용/할 일 조건 |
|---|---|---|
| `common/break-service` | 매장 설정의 중단·재개 시각 안내, 고객 문의·인수인계 | 브레이크 운영일에만. 음식점 외 업종도 사용 가능 |
| `food/service-reset` | 음식 취급 구역 정리와 승인된 보관 절차 확인 | 외식 공통. 셀프바 세부 절차는 셀프바 있을 때만 |
| `food/replenishment-review` | 다음 영업에 필요한 재료·도구의 부족 예외 확인 | 기존 재고 확인/보충 요청과 연결. 같은 대상을 이중 기록하지 않음 |
| `bonejjim/evening-prep` | 초벌 등뼈·육수 준비량 등 메뉴 전용 내용 | 해당 메뉴를 취급하고 실제 준비할 때 |

기존 `bonejjim/break`는 1→여러 개 분할의 migration 원본으로 남긴다. 기존 step-1→공통 안내, step-2→외식 정리, step-3→뼈찜 준비, step-4→보충 검토, step-5→인계에 대응표를 둔다. 휴식 전 인계와 재개 업무만 다루고 개인 휴게시간에 할 일을 배정하지 않는다. ‘쉬는 시간도 근무의 일부’ 문장은 공용 표준으로 옮기지 않는다.

영업 브레이크와 크루 개인 휴게는 별개다. 브레이크 없는 날은 브레이크 할 일을 생성하지 않는다. 필요한 위생 작업까지 사라지지 않도록 영업중/마감 정책은 별도로 설정한다. 자정을 넘는 영업, 요일별 브레이크, 임시 변경은 workplace 시간표와 영업일 경계로 계산한다. 고정 14:00/16:00이나 slot 이름으로 실제 시간을 추정하지 않는다.

## 5. 매뉴얼과 할 일의 관계

**매뉴얼=방법과 기준, 실행 TAP=누가 언제 어떤 결과를 확인할지, Task=그 TAP 안의 행동.** 하나의 매뉴얼을 여러 TAP에서 참조할 수 있고 하나의 TAP도 여러 매뉴얼을 참조할 수 있다. 세부 설명을 모두 체크박스로 만들지 않는다. 서로 다른 담당·시각·배치의 행동은 TAP을 분리한다. Task별 배정은 다시 도입하지 않는다.

| 사용자 선택 | 용도 | 예 |
|---|---|---|
| 필요할 때 보기 | 참고 매뉴얼. 업무 누락 아님 | 레시피 배합, 플레이팅 사진, 맛이 달라졌을 때 해결법 |
| 정기적으로 확인 | 정해진 영업일/시점의 점검 | 오픈 냉장 설비 확인, 마감 청소 |
| 작업할 때 확인 | 실제 입고/개봉/제조/해동 사건에 연결 | 국물 배치 냉각, 떡 개봉 후 보관 |

현재 지원: 매뉴얼 OFF, 일/주 반복 및 기존 준비·주문 전용 경로. **입고/개봉/냉각 사건 엔진과 상태 진단 UI는 신규 구현 필요**하다. POS/배달앱 연결을 초기 설정에 다시 넣지 않고, 우선 ‘배치 만들기/개봉 기록’의 짧은 수동 입력을 사건 원본으로 사용한다.

할 일 미표시의 진단은 다음과 같이 구분한다. 체크리스트 등록률 100%를 목표로 삼지 않는다.

| 진단 | 표시/행동 |
|---|---|
| 참고용으로 지정됨 | 정상 상태. 경고/매일 알림 없음 |
| 요일·조건·사건 대기 | 다음 예정 또는 ‘개봉할 때 생성’ 표시 |
| 파트·시점·제품 조건 미완료 | 사장/매니저에게만 ‘설정 필요’, 관련 항목만 수정 |
| 숨김/보관/다른 파트 필터 | 현재 보이지 않는 이유 안내, 권한 우회 노출 금지 |
| 대상 크루 공석 | 책임 파트의 공석 상태. 임의로 다른 크루에게 전가하지 않음 |
| 생성돼야 하는데 실행 없음 | 서버 생성 오류로 구분, 재시도/진단. 무조건 ON 유도 금지 |
| 같은 점검이 이미 연결됨 | 기존 실행으로 연결, 이중 체크 방지 |

진단은 클라이언트 추측이 아닌 실제 생성 조건과 동일한 서버 평가 함수를 사용한다. `intendedUse` 미지정인 기존 OFF는 참고용으로 자동 확정하지 않고 `unclassified`로 보존한다. 관리자에게 최초 검토 목록으로만 모으고, 모두에게 매일 배지를 띄우지 않는다.

## 6. 설정과 일상 화면 제안

신규 등록에서 업종·메뉴·재료·영업시간·파트는 이미 받은 값을 재사용한다. 메뉴에 따라 필요한 공정을 추론하되 ‘직접 제조/완제품’, ‘당일 소진/보관’처럼 모르는 조건만 한 화면 최대 3개 묻는다. 제품별 안전조건 입력이 길어지면 해당 매뉴얼의 설정 필요 상태로 남기고, 검증되지 않은 기본값으로 완료 처리하지 않는다.

설정 마무리는 다음 순서다.

1. 우리 매장에 필요한 매뉴얼 묶음 미리보기: 공통 운영 + 실제 메뉴/재료의 공정. 없는 장비/메뉴 추천 제외.
2. 업무 연결: ‘기본 점검 사용 / 직접 고르기 / 매뉴얼만 보관’의 세 선택. 기본 점검도 적용 예정 파트·시점·체크 수를 먼저 보여주고 명시적 적용.
3. 기존 시간표/파트를 활용한 변경 요약. 저장 후 ‘매뉴얼 보기’와 ‘오늘 할 일 보기’로 연결 결과 확인. 추가된 지식 수와 매일 체크할 항목 수는 별도 표시.

기존 설정에서는 같은 명칭·컨트롤을 재사용한다. 매뉴얼 상단에 ‘보기만 / 정기 확인 / 작업할 때’, 그 아래 담당 파트·시점 요약과 ‘연결된 업무’를 둔다. 메뉴/재료 화면에서도 같은 원본 지식에 접근한다. 크루에게는 할 일 한 줄과 ‘방법 보기’를 먼저 보여주고 근거·상세 조리법은 펼쳐 본다.

짧은 화면은 질문 수를 줄이는 원칙이지 필수 안전 점검을 3개로 자르는 규칙이 아니다. 정상적인 저위험 묶음은 결과 확인을 간단히 할 수 있지만, 온도·시간·수량 등 실제 증거가 필요한 작업을 ‘모두 완료’로 대신하지 않는다. 이상 시에만 사유/조치를 추가 입력하고, 사진은 모든 일에 의무화하지 않는다. 같은 시간에 완료를 반복 요구하는 팝업도 만들지 않는다.

## 7. 레시피·현장 노하우의 콘텐츠 단위

각 문서는 ‘언제 쓰는가 → 재료/장비/전제 → 방법 → 정상 기준 → 흔한 실패와 대응 → 연결 업무 → 출처/버전’ 순서다. 레시피는 배합 기준 수량·단위·수율, 준비물, 공정, 제공 기준, 보관 연결, 알레르기 확인을 구조화한다. 배합을 배수로 늘릴 수 있어도 가열/냉각 시간까지 비례 확대하지 않는다. 현장 시험 없이 ‘상업 운영 검증 완료’ 표시를 하지 않는다.

안전 근거, 제품 설명서, 맛·식감 노하우, 현장 가설을 구분해 저장한다. 예컨대 식감을 위한 보관 팁이 안전 보관조건을 덮어쓰지 못한다. 원가·수율·선입선출·분리 보관·불량 판별·실패 복구까지 조사 후보로 포함하되 확인하지 않은 효과/수치를 만들어내지 않는다.

| 사례 | 매뉴얼에 담을 내용 | 제안 실행 TAP | 아직 확인할 것 |
|---|---|---|---|
| 짬뽕 국물 | 기본 육수/해산물 포함 완성 국물 구분, 제조량·용기·냉각 장비, 소분·냉각·표시·보관·재사용 공정, 이상 대응 | 배치 생성 → 냉각 시작 기록 → 승인된 기준에 따른 확인 → 보관 위치/라벨 확인. 다음날 동일 설명 전체를 체크하지 않음 | 제품/배합, 실제 냉각 성능, 허용 시간·온도·보관기간의 국내 적용 근거. 특정 며칠을 공통값으로 제공하지 않음 |
| 떡 | 냉장/냉동/실온 유통 제품, 밀봉/개봉/해동/불림/조리 상태, 제조사 표시, 품질 변화를 나눔 | 입고 시 표시 확인 → 개봉/해동 사건의 대상 로트만 라벨·보관 확인 → 설정된 시점의 사용 판단 | 제조사별 개봉 후 조건, 불림 과정·보관 한계. ‘물에 담가 며칠’ 같은 일반화는 보류 |
| 공용 튀김 공정 | 생재료 교차오염 예방, 장비 사용과 기름 관리, 실제 메뉴별 익힘 기준 | 장비/기름 점검은 공용 1회, 메뉴별 기준은 해당 제조 실행에서 참조 | 치킨 기준을 돈까스에 단순 치환하지 않고 식재료/두께/장비 차이 검토 |

위 표는 실행/콘텐츠 설계 예시이며 지금 사용 가능한 완성 보관 SOP가 아니다. 필요한 안전값이 미확정이면 해당 실행 정책은 활성화하지 않고 ‘기준 확인 필요’로 표시한다. 보관 이력이 불명확한 식품을 재가열로 정상화하는 흐름은 만들지 않는다.

## 8. 데이터 계약과 구현 경계 (proposed)

| 모델 | 필요한 필드 | 경계 |
|---|---|---|
| `KnowledgeDocument` | knowledgeId, version, contentKind, scope, topicIds, applicability, phaseIds, sourceClaims, recipe/process/quality sections | 공용 원본. 매장 담당자·재고·일정 없음 |
| `StoreKnowledgeBinding` | workspaceId, knowledgeId, appliedVersion, localOverrides, reviewStatus, linkedMenuIds/itemIds | 공용판과 매장판 연결. 개인화 차이/안전 검토 필요 추적 |
| 실행 TAP | 기존 templateId/settings + knowledgeRefs(버전/필요 섹션), intendedUse, triggerPolicy | 운영 설정의 유일한 원본. 문서에 일정 중복 저장 금지 |
| `WorkEvent` | workspaceId, eventId, kind, subjectId/lotId/batchId, occurredAt, revision | 수동 생성부터 시작. 사건 수정/취소도 이력 보존 |
| 실행 발생 | 기존 tasks + occurrenceKey, eventRef, evidence, knowledgeVersion snapshot | 기록 재현, 동시 완료 CAS, 영업일과 경과시간 구분 |
| 연결 진단 | state, reasonCode, nextOccurrence, blockingFields, existingExecutionId | 서버에서 계산. 실제 배정/권한과 같은 조건 |

`triggerPolicy`는 임의 스크립트가 아닌 서버가 허용한 필드/종류만 받는다. 공용 `suggestedUse`는 권고이고, 실제 `intendedUse`는 매장이 저장한다. 중복키는 매장+정책+실제 발생(영업일/시간대 또는 eventId)+대상 배치/로트로 구성한다. 날짜만으로 다른 국물 배치를 합치지 않는다. 같은 재료에 체크가 두 번 있어도 ‘입고 상태’와 ‘냉각 완료’처럼 관찰 목적이 다르면 삭제하지 않는다.

달력 일정은 한국 영업일 경계, 냉각 경과시간은 실제 timestamp를 쓴다. 도중에 일정/문서가 바뀌어도 시작·완료 실행을 덮어쓰지 않는다. 매장 권한은 직책이, 업무 분류는 파트가 결정한다. D-017 재고 확인은 마지막 발주 후 N일의 별도 정책이며 새 개봉/냉각 사건이 그 기한을 미루면 안 된다.

신규 schemaVersion/검증·DB 발행·서버 projection·Flutter 소비를 함께 구현해야 한다. 기존 `contentFields`에 운영 설정을 추가하지 않는다. 구버전 앱에는 이해 가능한 콘텐츠만 projection하고 지원하지 않는 trigger 설정을 저장하지 못하게 한다. 검색 taxonomy/구성/가져오기/동기화는 요청당 같은 공용 발행본을 사용한다.

## 9. 업데이트 에이전트

이번 작업에서 기존 5역할 중 researcher/editor/reviewer/qa의 프롬프트에 아래 점검 지침을 추가한다. 실행/출력 스키마는 변경하지 않고 claims·unresolved·applicability·changeSummary·findings·checks에 담는다. **프롬프트 지침 추가와 기능의 강제 검증 구현은 다르다.** 새 job은 새 프롬프트 snapshot을 사용하고 기존 job은 고정 입력을 유지한다.

- 조사: 공통/공정/메뉴 적용 범위, 필요한 사건, 숨은 준비·보관·실패 대응, 제품 상태별 차이를 근거 주장과 연결.
- 편집: 방법 문서와 핵심 체크를 구분. 체크할 필요가 없는 팁에 억지 완료 항목을 만들지 않음. 분할은 새 sourceId 후보와 구→신 대응표를 changeSummary에 기록.
- 검토: 공통에 특정 메뉴/시각 혼입, 같은 작업의 중복 체크, 안전조건 미확인, 배치/로트 차이 누락을 확인.
- QA: 브레이크 없는 날/다른 업종/다른 제품 상태/개인화 매장에서 반례를 점검. 실행되지 않은 서버 테스트를 pass라고 기록하지 않음.

Aside 공개 조사 → 주장/조건 → 편집 → 독립 검토 → QA → 공급자 초안 → 명시적 공용 발행의 기존 경로를 유지한다. 요청형 실행이며 자동 예약/자동 발행은 켜지 않는다. 신규 sourceId·여러 개 분할은 현재 export-release의 기존 TAP 수정 병합만으로 처리할 수 없으므로 신규 발행/이관 구현이 필요하다. 현장 매장 비법은 매장 전용이 기본이며 소유자의 명시적 공유 없이 공용 연구/발행으로 복제하지 않는다.

## 10. 이관·검증 순서

1. **분류 정리**: 86개 원본에 scope/적용 조건 검토표 작성 → 공통 브레이크/메뉴 준비 분할 초안 → 공급자 검토. stable ID 대응표와 이전 콘텐츠 보존. 공용 DB 발행 없이 로컬 SOURCE만 바꾸고 운영 수정 완료라고 하지 않는다.
2. **연결 가시화**: 실제 생성 함수와 공유하는 진단 도입, 참고용/설정필요 구분, 기존 설정에서 연결 결과 미리보기. 기존 ON/OFF·시간표는 임의 변경하지 않는다.
3. **지식 링크**: 레시피/보관 문서의 버전 참조와 메뉴/재료 연결. 기존 양식·시작/완료 기록 보존, 개인화 매장은 비교 후 선택 적용.
4. **사건 실행**: 배치/개봉/입고 기록과 멱등 발생, 측정/예외 입력. POS 없이 수동 사건으로 검증한 뒤 확장.
5. **확대 검증**: 실제 운영 피드백으로 불필요 체크·미연결 중요 작업·설정 시간/완료 탭 수·재입력·이상 조치 미해결률을 측정. 완료율만으로 품질을 평가하거나 수집 전 개선율을 약속하지 않음.

필수 수용 시나리오: 치킨/카페/중식/뼈찜 및 음식점 외 업종에서 공통 브레이크에 등뼈·특정 영업시각이 없음; 브레이크 없는 날 비생성; 공통 정리와 메뉴 준비의 연결 중복 없음; 참고용 OFF 정상; ON인데 생성 불가 사유 표시; 동일 사건 재시도/동시 요청은 한 번 생성; 다른 배치 구분; 중요 측정은 일괄 완료 불가; 개인화/기존 완료 snapshot 보존; 권한/매장 전환/자정 경계/시간표 수정 검증; 과거 발주 재고 확인 기한 불변.

이번 완료 범위: 소스 감사, 공식 자료 조사, 이 설계와 에이전트 지침 보강. 미실시: 운영 DB 조회·발행·이관, 새 Flutter UI, 이벤트 엔진, 실매장 레시피/보관 시험, 네이티브·웹 배포. 세부 구현은 위 순서의 후속 작업이다.

검증 기록: content_team/content_memory Node 테스트 31개 통과, UI/settings 관계 검사 51개 통과. 소스 감사 집계와 Aside 조사 원문/요약은 `.local/manual-taxonomy-research/`에 보존. Flutter 소스 변경이 없어 이번에는 Flutter 분석·빌드·위젯 테스트를 실행하지 않았다.
