# 실제 매장 편집 전환 계획 · 2026-09-26

## 목적과 현재 상태

사용자는 Supabase와 현재 앱 구조를 실제 로그인 사용자가 수정하고 편집할 수 있게 요청했다. Astra 검토 결과, 로그인 계정별 Supabase 저장, 역할 확인, 서버 전용 원본 state, revision 충돌 방지, 체크리스트·근무·배치 등의 저장은 이미 구현되어 있다. 가장 큰 간극은 새 계정이 자동으로 합성 주문과 가상 직원이 있는 매장을 받고, 매장 정보·원재료·메뉴를 앱에서 추가하거나 수정할 수 없다는 점이다.

## 이번 적용 범위

1. 새 계정이 샘플 매장과 빈 매장 중 시작 방식을 명시적으로 선택한다. 기존 계정의 저장 데이터는 자동 전환하지 않는다.
2. 사장은 매장 이름과 설명을 수정한다. 사장과 매니저는 원재료 및 메뉴를 추가·수정·보관한다. 권한은 UI와 Edge Function 모두에서 확인한다.
3. 수량 변경은 기존 실사 기록으로 처리해 확인자·시간과 발주 후 N일 재확인 규칙을 보존한다. 연결된 미입고 발주, 진행 중 주문, 준비품 사용 설정은 보관 전에 확인한다.
4. 보관은 안정적인 ID와 과거 주문·업무 기록을 유지한다. 활성 선택 목록과 과거 보고를 구분한다.
5. 편집 시작 시 revision을 고정한다. 409 충돌이나 네트워크 실패 시 입력값을 유지하고 저장 실패를 명확히 보여준다. 공개 미리보기는 저장되지 않는다.

## 보안과 경계

Auth 사용자는 서버가 검증한 매장 membership과 역할로만 작업한다. 브라우저에 Supabase service key, 원본 운영 state 또는 다른 역할의 급여 데이터가 노출되면 안 된다. 기존 `.local/` 데모 데이터는 클라우드 매장으로 복사하지 않는다. 주문·매출 샘플, 공급업체 발주, 급여 계산은 실제 외부 서비스나 지급으로 표현하지 않는다.

다른 Auth 계정을 같은 매장에 초대·연결하는 정책과 UI는 **proposed**다. 현재 새 계정 GET은 개인 매장을 자동 생성하고 membership은 사용자당 하나로 제한된다. 팀 연결에는 초대 토큰, 만료, 승인, 원자적 membership 및 Tapper 연결, 기존 개인 매장 처리 규칙이 함께 필요하다. 명부에 이름을 더한 것을 계정 초대라고 표시하지 않는다.

## 확인 기준

새 계정의 명시적 시작, 실제 저장 후 재접속, 사장·매니저·크루 권한, 서로 다른 계정의 데이터 분리, 낡은 revision의 409, 빈 매장의 샘플 재생성 방지, 연결 기록을 가진 메뉴·원재료 보관 제한, 발주 후 재확인 기한, 공개 미리보기 저장 차단을 확인한다. 실제 직원 개인정보나 실제 공급업체 주문을 검증 데이터로 사용하지 않는다.
