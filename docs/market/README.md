# 매뉴얼 마켓 운영

현재 공통+12개 산업 탐색 영역에 86 TAP / 272 Task가 들어 있습니다. 기존 27개 컬렉션의 64 TAP / 211 Task는 모두 보존합니다. 기존 `docs/wiki/CHECKLISTS.md`와 `docs/wiki/checklist-library.json`에서 준비된 내용을 이관했습니다. 출처를 참고한 편집 제안이며 `basis`와 검토일을 화면에 표시합니다. 업종별 현장 검토가 완료됐다는 의미는 아닙니다.

## 매장에서 사용

- 매뉴얼 → **매뉴얼 마켓**에서 업종·업무를 검색하고 법적 기준/운영 업무를 골라 담습니다. 마지막 확인에서 업무별 자동 분류 또는 기존 그룹 하나로 가져옵니다. 우리매장 → 매장 준비 → 할일 준비도 마켓으로 연결합니다.
- 추가된 TAP은 사용 OFF 상태입니다. TAP 상세 → **파트·시간대·TAP 운영 설정**에서 배정과 사용 여부를 설정합니다.
- 공용 연결 TAP의 내용·Task·매뉴얼은 새 공용 발행본 배포 후 다음 서버 조회에서 자동 반영됩니다. 매장의 그룹·파트·시간대·완료 방식 등 운영 설정과 이미 생성된 업무는 유지합니다. 앱의 기존 30초 조회/서버 분 단위 캐시 정책을 사용하며 백그라운드 앱에는 다음 활성화 시 반영합니다.
- 제목·Task 내용·순서를 직접 수정하면 그 TAP 전체가 **개인화**로 분리됩니다. 공용 연결을 남기려면 TAP 상세에서 **개인화 사본 추가**를 선택합니다. 그룹 이동과 운영 설정만 바꾸면 연결을 유지합니다.
- 매뉴얼 → **백업·복원**에서 개인화·자체 작성 TAP을 기기 저장하거나 JSON 파일로 내보내고 다시 가져옵니다. 복원은 기존 항목을 덮어쓰지 않고 새 개인화 사본을 추가하며, 사용 OFF/배정·장소 연결 해제로 시작합니다. 반복·완료 규칙은 유지합니다.
- 백업은 공유 양식의 개인화 콘텐츠를 기기에 복사하는 기능입니다. 기기 백업은 매장/사용자별로 구분하며 브라우저 데이터 삭제 시 사라질 수 있으므로 파일로도 보관합니다. 공용 연결 원본, 크루 식별자, 출퇴근·급여·업무 수행 기록, 인증 정보는 내보내지 않습니다. 사진·영상은 HTTPS 링크만 포함합니다. 파일은 UTF-8 JSON, 최대 2MB입니다.

## 제공자가 공용 자료를 개선하는 절차

1. `SOURCE.md`의 `tap2work-tap` JSON 코드 블록을 편집합니다. TAP의 `sourceId`, Task의 `id`는 같은 항목의 개선이라면 유지합니다. 새 항목에는 새 ID를 부여합니다. 업무 내용과 매뉴얼을 함께 검토하고 출처 URL, `reviewedAt`, `basis`를 갱신합니다. 임의 Markdown 문장 전체를 자동 해석하는 업로더는 아닙니다.
2. `npm run market:build`를 실행합니다. 형식, ID 중복, Task별 운영 정책 혼입, 링크와 글자 수를 검증하고 내용 해시를 ID로 하는 `releases/<sha256>.json`과 `current.json`을 만듭니다. 기존 release 파일은 수정하지 않습니다.
3. `npm run market:check`, `npm run test:console`, `npm run check`를 통과시키고 MD와 두 JSON 발행본을 함께 코드 리뷰/커밋합니다. 과거 발행본은 유지합니다.
4. 기존 배포 절차로 Supabase `operations` 함수를 배포합니다. 공용 자료는 서버 배포본에서 읽으므로 앱 재설치 없이 연결된 매장이 다음 조회에서 갱신됩니다. 공개 샘플도 갱신할 때는 Pages 빌드를 함께 배포합니다.

공용 발행 권한은 저장소/서버 배포 관리자에게만 있습니다. 매장 사장/매니저의 편집 API는 자기 매장만 수정합니다. 정기 콘텐츠 수집·전문가 검토·자동 발행, 공용 원본 웹 편집기, 3-way 병합 UI, 충돌 후 자동 재적용, 암호화 백업, 사진 파일 번들, 기기 간 개인 초안 동기화는 이번 구현에 포함하지 않습니다. 명시적 사용자 수정은 공용 업데이트에서 분리하므로 3-way 병합을 요구하지 않습니다.

## 개발 계약

`manual_market.mjs`는 공용 출처 연결(`catalogLinks`), 생성 요청 receipt(`catalogOperations`), 업데이트 전 양식 이력(`catalogHistory`)을 별도 상태 섹션으로 관리합니다. 이력/receipt는 클라이언트에서 숨깁니다. source 연결과 백업 투영은 업무 편집 권한이 있는 사장/매니저에게만 전달합니다. 기존 양식을 공용 연결로 소급 전환하지 않습니다.

모든 공유 저장은 서버 권한과 revision CAS 검증을 거칩니다. 추가/가져오기/복원/사본 생성의 operation ID는 성공 후 같은 사용자·내용 재시도에만 기존 결과를 반환합니다. 실패는 원자적으로 폐기합니다. 원본 업데이트는 콘텐츠 해시가 마지막 적용본과 같은 연결만 수정하고, 이미 생성된 모든 실행 snapshot은 그대로 둡니다.
