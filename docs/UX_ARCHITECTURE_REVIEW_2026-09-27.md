# 업무 UX 및 주문 수용 구조 검토 · 2026-09-27

## 이번 대화에서 확인한 범위

사용자는 보고서를 참고해 디자인과 전체 구조를 개선하되 중요한 방향을 질의하도록 요청했다. 후속 질문에 다음을 선택했다.

- 업무·매뉴얼 UX 개선과 주문 연동을 위한 구조 정비까지 진행한다.
- `주문처리중 / 할일 / 완료` 보드와 TAP → Small TAP, BIG TAP 그룹을 유지한다.

자체 POS 결제·영수증 구축, 별도 KDS 화면, 상태 관리 패키지 교체는 이번 구현 범위에 포함하지 않는다. OKPOS는 현재 사용 제품으로 기록되어 있지만 API 계약·접근 권한은 확인되지 않았다.

## 코드에서 확인한 현재 구조

`OperationsController`가 HTTP 요청, JSON 해석, 인증 헤더, 5초 조회, 화면 상태, 공개 체험의 메모리 변경을 함께 관리했다. UI는 `Map<String, dynamic>` 형태의 매장 스냅샷을 사용한다. 서버의 `developer/operations.mjs` 및 기능 모듈이 역할별 응답, revision 충돌, 주문·준비품·입고 규칙을 적용한다. 로그인 저장은 Supabase 경로, 비로그인 체험은 읽기 전용 샘플 경로다.

현재 구조에서 상태 관리 패키지 전체 교체보다 통신 경계를 먼저 분리하면, 기존 동작을 검증하면서 연동 기반을 정리할 수 있다.

## 이번 구현

1. TAP 카드의 드래그·완료·상세 열기 영역을 최소 48 Flutter 논리 픽셀로 확보했다. 기존 한 줄 제목을 유지하고 툴팁으로 전체 제목을 제공한다. 글자 배율이 커지면 상세 열기는 접근성 이름을 가진 화살표로 줄여 제목 공간을 확보한다.
2. Small TAP 매뉴얼에 소속 TAP 이름을 표시하고 팁을 별도 안내 영역으로 구분했다. 방법을 읽는 동작과 완료 동작은 계속 분리한다.
3. 순수 Dart `OperationsRepository` 인터페이스와 `OperationsResult`를 도입했다. HTTP·JSON·인증 헤더·타임아웃은 `HttpOperationsRepository`로 옮겼다. 컨트롤러에 저장소를 주입할 수 있으며 기존 생성자 호출도 유지한다. 주입한 저장소의 수명은 컨트롤러가 소유하고 dispose 때 닫는다.
4. 공개 샘플 저장소는 직접 호출하더라도 쓰기를 거부한다. 기존 revision 전달, 403/409 후 새로고침, 세션 토큰 재조회, 서버 역할 투영과 미리보기 정책을 유지한다.

이는 **통신 경계 분리의 첫 단계**다. JSON 스냅샷과 HTTP 상태 코드 기반 결과, 컨트롤러의 기본 HTTP 저장소 생성, 화면 내부 일부 규칙은 남아 있다. 완전한 클린 아키텍처, 주문 제공자 어댑터 또는 오프라인 동기화가 구현된 것은 아니다.

## 제공 보고서의 적용·정정

| 주제 | 검토 결과와 적용 방향 |
| --- | --- |
| 칸반 | 이미 보드가 있다. 일반적인 To Do / In Progress / Done으로 바꾸면 D-031과 충돌한다. 사용자 답변대로 현행 열을 유지한다. |
| 접근성 | 48px 조작 영역, 큰 글씨와 긴 내용 검증은 적용한다. 모든 위젯에 스크롤 래퍼를 씌우기보다 화면별 제약과 중첩 스크롤을 확인한다. |
| 상태 관리 | BLoC/Cubit/Riverpod은 화면 상태 도구다. 기기 간 전달에는 별도 서버 이벤트/조회 경로가 필요하다. 이번에는 기존 ChangeNotifier를 유지한다. |
| 클린 아키텍처 | 저장소 경계를 먼저 만들고 업무별 모델을 단계적으로 분리한다. Flutter 공식 가이드도 도메인 계층의 필요성을 복잡도에 따라 판단하도록 안내한다. |
| DoorDash | Drive 배달 이벤트와 Marketplace 주문 수용은 별개 계약이다. `external_delivery_id`를 모든 채널의 주문 ID로 일반화하거나 배달 생성 이벤트만으로 메뉴 주문을 만들지 않는다. |
| 알림·긴급 색상 | 색상과 함께 상태·시간을 표시한다. 소리·점멸·목표 시간은 현장 선택과 타이머 정책이 필요하다. 샘플 목표 시간을 실제 조리 기준으로 승격하지 않는다. |
| 재고 | 모든 품목에 ‘5개 이하’를 적용하지 않는다. 기존 품목별 부족 기준과 주문 조리 시 준비분 차감, 입고 시 원재료 증가, D-017을 보존한다. |
| 오프라인 | 로컬 저장만으로 다기기 일관성이 보장되지 않는다. 우선 캐시 읽기, 쓰기는 별도 outbox·중복 방지·충돌 해결 설계 후 검토한다. |

## 후속 구조 제안 — proposed

```text
Flutter 업무 화면 → 화면 컨트롤러 → 업무별 저장소 인터페이스
                                      ↑ 구현
                             데이터 계층 → 매장 백엔드

외부 POS/주문 제공자 → 제공자별 수신 어댑터 → 이벤트 검증·중복 방지
                                            → 주문/조리/배달 상태
                                            → TAP 생성·준비품 처리
```

다음 단계에서는 주문에 한정해 불변 `Order`, `OrderLine`, `OrderSource` 모델과 매핑 테스트를 추가하는 방안을 제안한다. 준비품·발주·매뉴얼 모델은 해당 기능 변경 시 분리한다. 모든 폴더를 한 번에 이동하거나 새 프레임워크를 필수로 넣지 않는다.

실제 연동 전에는 제공자·매장·외부 주문 ID의 복합 키, 이벤트 ID 또는 제공자 규약에 맞춘 중복 방지 키, 취소/변경/역순 이벤트, 인증 검증, 영속 이벤트 기록과 트랜잭션, 재시도 및 운영 관측을 정의해야 한다. 주문 수용 상태, 조리 상태, 배달 상태를 별도로 둔다. 기사 픽업 이벤트는 조리 완료나 재고 차감을 다시 실행하는 트리거가 아니다. 외부 상태 전송은 outbox 등 실패 복구 가능한 서버 경로가 필요하다. 제공자별 인증 방식을 확인하며 모든 서비스가 같은 서명 규약을 갖는다고 가정하지 않는다.

SOP 타이머는 개인 기기 타이머인지 팀 공유 타이머인지 먼저 결정해야 한다. 공유 타이머라면 시작·종료 시각, 중지/재개 권한, 앱 재시작, 기기 시간 차이, 알림 전달 실패를 처리해야 한다. 타이머 종료를 작업 완료나 식품 안전 확인으로 자동 처리하지 않는다.

중요한 다음 질문은 실제 연동을 시작할 때의 **OKPOS 주문을 조회만 할지, 앱에서 조리 상태를 회신할지**, 타이머를 추가할 때의 **개인용/팀 공유 범위**, 오프라인 기능을 추가할 때의 **조회/쓰기 허용 범위**다. 현재는 미확정 제안으로 남긴다.
