# 신규 매장 등록·설정 연결 점검 · 2026-10-08

사용자 요청: 새 매장 등록은 화면마다 1~3개 질문에 답하는 단계형 흐름으로 구성한다. 기존 설정과 항목·저장 효과를 통일하고 치킨·한식·돈까스 등 업종에 따라 기본 TAP/Task를 준비한다.

## 점검 결과와 처리

| 영역 | 이전 문제 또는 구분할 값 | 이번 처리 · 저장 원본 |
|---|---|---|
| 첫 매장/추가 매장 | 첫 매장은 빈 매장 즉시 생성, 추가 매장은 이름만 입력 | 두 진입 모두 `StoreSetupScreen` → 최종 확인 → `create_workspace` 단일 요청 |
| 매장 업종/매뉴얼 업종 | 프로필 식당·카페와 마켓 외식 분류가 따로 선택됨 | `profile.businessTypeId`에 14개 세부 업종, `industryId`는 호환 대분류. 같은 서버 metadata로 등록/기존 프로필 표시. 기본 매뉴얼 구성은 선택 업종을 바탕으로 미설치 항목을 제안 |
| 영업시간 | profile.hours와 workplace.days 두 저장 모델, 프로필 운영 탭에서 다시 진입 | 신규 등록은 `workplace.days/breaks/businessDayStart`만 저장. 기존 공통 영업시간 편집기에서 요일·교대·브레이크 수정. legacy profile.hours는 읽기 호환만 유지 |
| 크루 수·필요 인원 | 프로필의 선언 크루 수/채용 목표 인원과 인원 배치가 혼재 | 별도 크루 탭 입력 제거. 실제 크루는 `tappers`, 교대별 필요 인원은 `workplace.days[].headcounts`, 실제 이름 배정은 `crewIds`. 기존 채용 초안/이력 데이터는 삭제하지 않음 |
| POS/배달 설정 | ‘설정했어요’와 ‘사용 중’ 이중 스위치 | POS: 나중에/미사용/제품, 배달: 나중에/미사용/사용. `configured/enabled` 저장 호환, 제품/플랫폼 세부정보 유지 |
| 주문 도구/주문 보드 | 프로필 안과 우리매장에 주문처리 시스템 진입 중복 | 프로필 안 중복 진입 제거. 우리매장 주문처리 보드 설정 유지. POS 사용 정보와 실제 외부 주문 연결은 다른 의미이므로 병합하지 않음 |
| 설정 진입 | 가로 탭을 탐색해야 POS/배달·크루·운영 발견 | 우리매장에 매장 정보/POS/배달 플랫폼/기본 매뉴얼 구성 직접 진입. 각 편집은 해당 영역만 저장. 목록에 실제 업종/POS제품/플랫폼/영업일·시간·교대/파트/TAP 수 요약 |
| 매뉴얼 구조 | 세부 업종 선택 후 수동 검색·가져오기 필요 | 공용 발행본에서 외식 공통+선택 업종+배달(해당 시)을 제안. 목적별 폴더 → TAP → Task/방법, 항목별 제외·본문 미리보기. 돈까스는 기존 치킨·튀김 컬렉션의 튀김 공통 콘텐츠 사용을 명시 |
| TAP 실행 | 자료 가져오기와 오늘 실행을 혼동할 수 있음 | 기본 OFF. 명시적으로 업무 사용을 켜면 등록 시 선택한 영업 요일로 반복 설정. 법적 참고·다른 업종·실제 레시피 자동 생성은 없음 |
| 주소/안내 | 등록 후 별도 기본 정보 입력 | 등록 단계의 선택 입력 2개 → `profile.address/arrivalNote`. 이후 매장 정보에서 같은 값 수정 |
| 정산·권한·인증 | 의미가 다른 고급 설정을 신규 등록에서 자동 확정할 위험 | 기존 정산·직책 권한·출퇴근 인증 설정 진입/서버 계약 유지. 초기 완료 화면에서 크루·메뉴·재고·배치도 등 후속 설정 위치 안내 |
| 재고/발주 | 매장 등록과 실제 재료·거래처·수량은 별개 | 기존 재고·발주/메뉴·재료 편집 유지. 샘플 재고·실제 발주·공급자 요청 생성하지 않음. D-017 일수 정책 유지 |
| 근무표·크루 | 필요 인원을 실제 고용/배정으로 오인 | 신규 등록 시 가상의 크루·근무를 만들지 않음. 기존 크루 등록 → 인원 배치 → 근무표 편집으로 연결 |
| 기록/충돌 | 새 설정 적용이 기존 매장/개인화 매뉴얼을 덮어쓸 위험 | 생성 전 메모리 상태에 검증·조립 후 RPC 원자 생성. 다른 매장 불변. 기존 업종 수정은 기존 매뉴얼을 교체하지 않음. 기존 편집 opening revision/actor/workspace 검사 |

## 단계와 필드 수

13단계, 배달 선택 시 14단계. 1 매장 이름(1), 2 업종(1), 3 운영 형태(복수 선택 그룹 1), 4 주소·안내(선택 2), 5 영업 요일(1), 6 영업 시작·종료(2), 7 교대 수(1), 8 브레이크 여부·시작·종료(최대 3), 9 파트(복수 선택 그룹 1), 10 파트별 필요 인원(최대 3), 11 POS(1), 12 배달 플랫폼(해당 시 복수 선택 그룹 1), 기본 매뉴얼 선택·업무 사용(2), 최종 읽기 요약. 매뉴얼 후보는 TAP별 체크와 펼침 상세로 확인한다.

교대는 30분 단위로 균등 분할한 초기값이며 사용자가 다음 설정에서 경계·요일별 인원을 수정할 수 있다. 브레이크는 영업시간 내부만 허용하며 크루의 휴게/급여 시간을 자동 차감하지 않는다. 24시간 동일 시작·종료는 이번 간단 등록에서 허용하지 않는다.

초안은 열린 화면 메모리에서 유지한다. 이전/다음·키보드·실패 재시도·명시적 취소를 제공한다. 앱 종료 후 초안 복원은 미구현이다. 결과가 불명확한 재시도는 원래 requestId/payload를 유지한다. 서버가 생성 전 검증 거절을 명시한 경우만 초안 수정을 다시 열고 최신 목록을 확인한다.

## 서버 경계

- `business_types.mjs`: 제품의 세부 업종 metadata. 콘텐츠 원본이 아님.
- `store_setup.mjs`: 요청에 주입된 공용 발행본의 setup projection, 초기 설정 조립/검증. 기존 `saveStoreProfile`, `mutateWorkplace`, `mutateManualMarket`, `saveTapSettings` 재사용.
- `supabase_backend.mjs`: 인증 후 첫 GET에 setup choices 제공. 매장 생성 전에 모든 입력 검증. 이미 처리한 requestId는 `tap2work_workspace_requests`에서 먼저 조회해 변경된 catalog로 재검증하지 않고 기존 매장 반환. 반환 전 소속/권한 재검증.
- 기존 RPC/문서 section 저장 재사용. 새 migration 없음. 공용 DB 발행·기존 매장 운영 데이터 변경 없음.
