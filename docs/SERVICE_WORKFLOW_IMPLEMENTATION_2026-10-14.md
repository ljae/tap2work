## 주문 기능의 종료 경계

우리매장의 주문처리 시스템 연결 진입·토글과 해당 Flutter 폼을 삭제했다. 업무 보드는 할일/완료이며 주문 처리 레인·고객별 카드·그룹 이동/전체 완료·주문 목표시간 표시를 제거했다. 공개 미리보기의 고객 주문 완료·준비품 차감·대시보드 주문 상태 동기화도 제거했다.

서버는 고객 주문 TAP 생성과 완료 동기화/준비품 소비 코드를 삭제한다. 모든 역할에서 `orderBoardEnabled=false`, 현재 실행 투영은 고객 `orderId`가 있는 업무를 제외하고 대시보드 처리 큐는 비운다. 구 `save_order_system`은 소유자 요청에410, 비소유자에는 기존 권한 검사로403을 반환한다. 구 고객 업무에 대한 변경 요청은410으로 거절한다. 일반 업무 정렬의 대상에서도 구 고객 업무를 제외한다.

고객 주문/완료 증거는 저장소에서 삭제하거나 날짜를 새로 쓰지 않는다. 자동 생성용 과거 샘플 정의를 보관 처리하고 예약 그룹의 기본 이름 ‘주문처리’는 ‘주방 운영’으로 바꾸되 ID와 사용자 지정 이름은 유지한다. 재고 발주·입고와 레시피·준비품 생성/실측/완성 수량은 독립 기능이다. 고객 주문에 의한 준비품 자동 차감은 종료되고 기존 수량·이동 기록은 유지된다. POS/배달 기기의 정보·사용 매뉴얼은 외부 주문 연결 기능으로 승격하지 않는다.

## 데이터·권한 계약

`developer/service_workflow.mjs`가 `serviceBriefing`, 추가만 하는 `serviceRecords`, 서버 전용 `serviceReceipts`를 관리한다. 운영 API의 기존 인증된 매장·직책·revision 저장 계약과 도메인별 JSONB section persistence를 재사용하며 새 SQL 스키마나 외부 서비스는 추가하지 않았다.

`serviceWorkflow`는 별도 읽기 투영이다. 본인 근무는 한국 영업일 경계와 실제 현재 근무/승인 OFF 상태를 따른다. 시작 안내는 활성·등록된 매뉴얼 참조만 투영한다. 인계는 팀 공유, 연습은 본인/지정 버디/권한 리더, 의견은 본인/권한 리더에게 표시한다. 원시 사건·멱등 영수증·편집 원본은 직접 반환하지 않는다.

모든 새 변경은 actor/workspace 범위, 폼의 opening revision, requestId를 사용한다. 같은 actor/requestId의 동일 payload 재시도는 revision 변경 뒤에도 다시 기록하지 않는다. 다른 payload로 같은 번호를 재사용하면409다. 입력이 바뀌면 새 요청 번호를 사용한다. 버디 확인과 인계 처리 사건은 기존 사건의 작성자·시각을 덮어쓰지 않는다. 등록 후 일반 매뉴얼 저장에서도 serviceGuideId/sourceLocale을 보존한다. 최대5000사건/영수증 이후에는 조용히 이력을 지우지 않고 보관 공간 확인 오류로 중단한다.

앱의 `ServiceWorkflowDraft`는 기존 OperationsController/Repository를 사용하며 읽기 상세는 `showAppPage`, 입력은 공통 폼·고정 footer를 재사용한다. 입력 컨트롤은 시트의 퇴장 모션 후 실제 unmount에서 정리한다. 읽기·검색·인쇄·개선 의견·연습은 기존 Task 완료 API와 독립이다.
