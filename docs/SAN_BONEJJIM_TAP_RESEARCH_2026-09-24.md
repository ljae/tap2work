## Tap을 생성하는 기준

- BIG TAP `주문처리`에는 **주문 1건의 실제 처리**를 둔다. 주문번호/테이블/메뉴/수량/옵션/변경 사항을 가진 Tap instance이며, 새 주문마다 새 실행 ID를 만든다. 산뼈찜 2개를 주문한 한 테이블은 기본적으로 주문 묶음 1건으로 제안하지만, 주방 배정 단위가 다르면 메뉴 줄별 Tap으로 나누는 것이 가능해야 한다.
- BIG TAP `뼈찜 조리`, `뼈짬뽕 조리`에는 **주문 전 준비**를 둔다. 주방에서 미리 확인하는 재고·소분·육수/양념·사리 준비 등이며 특정 고객 주문 ID가 없다. 뼈곰탕 공통 육수 준비를 어느 그룹에 둘지는 실제 매장 R&R 확인이 필요하다.
- 주문별 Tap의 Small Tap은 해당 주문에서 **실제 해당하는 항목만** 생성한다. 뼈짬뽕 주문에는 화산뼈찜 맵기 확인을 넣지 않고, 사리 없는 주문에는 사리 포장·전달 항목을 넣지 않는다. 주문 수정 후에는 완료 기록을 지우지 말고 새 변경 이력을 남긴다.
- 주문 상태는 `할일 → 주문처리중 → 완료`를 쓴다. Tap을 직접 완료하면 해당 Tap의 미확인 Small Tap도 모두 같은 원자적 변경에서 완료한다는 사용자의 선택을 따른다. 이미 확인한 Small Tap의 actor/time은 보존한다. 고객 대기시간은 근무 시간이나 급여 실적으로 계산하지 않는다.
- 상세 매뉴얼은 `관찰된 제공 사례`, `현재 매장 기준 확인`, `실행 지시`를 구분한다. 실제 조리 지시는 사장/주방 책임자가 수치와 완료 기준을 확인한 뒤 게시한다. 확인 전에는 “매장 레시피/오늘 제공 기준 확인”이라는 placeholder를 쓴다.

아래 단계는 검증된 산 매장 SOP가 아닌 **Tap UI용 업무 분해안**이다. Small Tap은 제목을 짧게 하고 상세 매뉴얼에 확인할 필드를 쓴다.

| Tap 템플릿 / 생성 조건 | Small Tap 후보 | 상세 매뉴얼에 표시할 정보 |
| --- | --- | --- |
| 1. 주문 접수·분기 / 모든 주문 | 주문번호·테이블 확인 → 메뉴·수량 확인 → 옵션·제외 요청 확인 → 담당 라인에 전달 | 메뉴 줄마다 `메뉴명`, `수량`, `사이즈`, `맵기`, `사리`, `면/밥`, `추가 밥류`, `제외 요청`, `메모`, `주문 변경 시각`. 테이블 주문기기 사례는 있으나 실제 POS 연동 방식은 미정 [R2·R5]. |
| 2. 산뼈찜 본품 / 해당 메뉴 줄 | 사이즈·제외 요청 재확인 → 준비된 본품/양념 기준 대조 → 매장 기준대로 조리 완료 확인 → 동반 소스·사리 여부 대조 → 출고 표시 | 소·중·대 등 실제 판매 옵션, 고추 제외 등 허용 여부, 당일 소스 기준. R3의 관찰을 현재 고정 규칙으로 표시하지 않는다. |
| 3. 화산뼈찜 본품 / 해당 메뉴 줄 | 매운 단계 재확인 → 토핑·사리 대조 → 매장 기준대로 조리 완료 확인 → 당일 소스·국물 제공품 확인 → 출고 표시 | 주문 맵기, 추가 우동·떡튀김·주먹밥, 당일 소스/국물. R1·R4·R6의 제공 차이를 선택지로 처리한다. |
| 4. 뼈곰탕 / 해당 메뉴 줄 | 수량 확인 → 준비된 국물·뼈고기 기준 대조 → 매장 기준대로 마무리 → 동반품·포장/홀 구분 → 출고 표시 | 메뉴 변형, 밥 포함 여부, 소스 및 홀/포장 구성은 현재 매장 기준을 불러와야 한다 [R5]. |
| 5. 뼈짬뽕 / 해당 메뉴 줄 | 면/밥 요청 확인 → 준비된 국물·뼈·채소 기준 대조 → 매장 기준대로 마무리 → 면/밥 및 동반품 대조 → 출고 표시 | 면 대신 밥 요청 사례가 있다 [R5]. 현행 허용 여부와 추가금은 주문 데이터/승인 메뉴 기준에서 확인한다. |
| 6. 추가 사리·밥류 / 옵션이 있을 때만 | 사리/밥류 종류·수량 확인 → 제공 시점 확인 → 분리/함께 제공 기준 확인 → 본품과 매칭 → 전달 표시 | 우동·칼국수, 계란볶음밥, 식후 볶음밥, 주먹밥, 떡튀김을 서로 다른 option ID로 둔다. 제공 방식은 R1·R2·R4가 달라 오늘 기준 확인 필드가 필요하다. |
| 7. 홀 전달·최종 대조 / 홀 주문 | 주문번호·테이블 다시 확인 → 본품 수량 대조 → 조건부 사리·소스·국물 대조 → 뜨거운 음식 전달 알림 → 완료 | 앞접시·반찬 셀프 안내는 확인된 방문 경험 [R1·R2·R4·R5]을 참고한 후보. 실제 제공 방식은 현재 매장 안내를 사용한다. |
| 8. 포장·배달 전달 / 해당 채널일 때만 | 메뉴·옵션 대조 → 매장 승인 포장 기준 확인 → 구성품·밀봉 확인 → 주문번호와 포장 매칭 → 전달 표시 | 외부 후기가 실제 포장 구성·시간·온도를 증명하지 않는다. 주문표에 있는 항목만 대조하고 매장 기준과 포장 위생 지침을 별도로 확인한다. 실제 배달 플랫폼 연결은 범위 밖이다. |

**한 주문에 Tap을 몇 개 만들지:** 앱의 드래그 보드에서는 주문 묶음 Tap 하나가 이해하기 쉽다. 위 표의 2~8은 메뉴별 하위 단계 템플릿으로 조합할 수 있다. 주방과 홀의 별도 완료/담당 지정이 필요하면 동일 주문 ID를 공유하는 Tap을 역할별로 분리한다. 어느 방식인지는 실제 매장 인력 배치와 주문 흐름을 확인한 뒤 정한다. 같은 주문 메뉴를 두 번 계산하거나 중복 출고하면 안 된다.

## 현재 문서·코드를 고칠 때 먼저 확인할 지점

1. `docs/wiki/checklist-library.json`의 `bonejjim` 컬렉션은 현재 `bone-prep`, `broth`, `sauce-side`, `kitchen-peak` 등에 사전 준비와 주문별 수행이 섞여 있다. 이를 준비 BIG TAP과 주문처리 BIG TAP으로 분리하되 기존 template/task/step ID와 완료 기록을 버리지 않는다.
2. `kitchen-peak`의 **“우동사리는 별도 그릇”**은 R4와 충돌한다. 별도 제공을 확정 매뉴얼로 쓰지 말고 현재 메뉴/당일 기준으로 조건화한다.
3. `sauce-side`와 홀 안내의 **“특제소스는 산뼈찜에만”**은 R1 후기의 산뼈찜 전언을 사실로 키운 내용이다. R6의 화산뼈찜 마요소스 사례와도 구분한다. 소스 종류·메뉴별 제공 여부를 실제 매장에서 검수한다.
4. `broth`, `hall-peak`의 **“뼈곰탕 국물이 모든 주문에 기본 제공”**은 R1의 추정과 R4/R6/R7의 다른 경험 때문에 확정할 수 없다. 당일 제공 정책이나 품절 대체를 보여주는 조건부 항목으로 바꾼다.
5. `kitchen-peak`의 볶음밥은 **계란볶음밥 단품/추가**와 **식후 볶음밥 요청**을 주문 항목으로 분리한다. R1 글 자체도 식사 표현이 모호하다. 현재 판매 상품 관계는 매장 확인이 필요하다.
6. `bone-prep`, `broth`, `kitchen-peak`에 적힌 핏물·초벌·향신채·“찬물은 쓰지 않음”·완성 판정·화력 같은 조리 문구는 방문 후기에서 검증되지 않았다. 매장 책임자가 실제 레시피와 안전 절차를 승인할 때까지 실행 지시로 표시하지 않는다.
7. `docs/REVISION_TODO_2026-09-24.md`의 작업 B/C에서 이 조사 파일을 메뉴별 Tap 구성의 입력으로 참고한다. `PRODUCT.md`와 `docs/project-state.json`의 실제 구현/결정 기록은 구현 이후 최신 파일을 다시 읽고 갱신한다. 이 조사 자체를 CEO 승인이나 매장 공식 SOP 확정으로 기록하지 않는다.

## 매장에 확인할 짧은 질문

1. 현재 실제 판매 메뉴와 사이즈·맵기·옵션 조합은 무엇인가? 간장뼈찜, 백뼈짬뽕 등 후기에 보이는 변형은 지금도 판매하는가?
2. 뼈찜과 뼈곰탕·뼈짬뽕의 **주문 전 준비**를 어떤 주방 담당이 언제 완료하는가? 공유하는 육수/뼈 준비분은 무엇인가?
3. 산뼈찜·화산뼈찜·뼈곰탕·뼈짬뽕별 기본 소스/국물은 무엇이고, 품절 시 어떤 대체를 안내하는가?
4. 우동·칼국수사리는 메뉴별로 따로 내는가, 본품에 넣는가, 식후에 넣는가? 계란볶음밥과 식후 볶음밥은 별개 상품인가?
5. 뼈짬뽕의 면↔밥 변경과 뼈찜의 고추 제외 요청은 가능한가? 주문표에 어떤 코드로 표시하는가?
6. 준비분의 실제 레시피·중량·시간·온도·보관/폐기 기준은 누가 검수하고 변경을 승인하는가?

이 답변을 받은 뒤에만 실제 매장용 매뉴얼과 자동 생성 조건을 확정한다. 그전에는 가상 매장의 샘플 Tap으로 표시한다.
